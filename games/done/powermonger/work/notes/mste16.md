# Powermonger v1.2: Mega STE at 16 MHz (`pm_mste`, PMSixteen, 2026-11-19)

Tags: **[obs]** raw tool output (`/tmp/pm16/runs/*.out`, copied in part below; the run directories are not kept), **[INFERENCE]** not run. Hatari 2.6.1 only, private `HOME` (`/tmp/pm16/home`, every run additionally in its own `strun-*/home`), no real hardware, no MiSTer.

## 1. The problem and the register
* A Mega STE powers up at 8 MHz: `$FF8E21` (byte; word `$FF8E20`) reads 0. In Hatari 2.6.1 bit 1 = 16 MHz, bit 0 = the 16 KB cache (refused at 8 MHz: cache needs 16 MHz). Nothing in Powermonger, TOS 2.06 or HDDRIVER writes it (PMSpeed: `ff8e2` I/O trace over a whole boot); `--cpuclock 16` on Hatari's command line is ignored at boot (it only works as the `hatari-option` after boot).
* v1.1 on a Mega STE (the shipped floppy zip, 60 Hz, map view, 1000 VBL) [obs]: `RESULT mste_fl_v11 map view: sync $fc (60 Hz), fps 4.50 (75 flips / 1000 VBL), 1001 VBL = 16.7 s, 133581 cycles/VBL, world ticks 67 = 4.016/s, loop passes 67 = 4.02/s`, register `[('00', '00')]` at the end.

## 2. The patch (`patches/pm_mste.s`, default yes)
* An `init` routine (`; init: $dc200`, blob `$DC200..$DC247`, 72 B, `EXTRA_RANGES["pm_mste"] = [(0xDC200, 0xDC2FF)]`, the page after `pm_cachecap`'s, inside p6_'s range and the HD overlay window). `init` is core.s's supervisor start-up call (`front` -> `uinit` -> `Super(0)` -> `init`), common to the floppy and the HD build, before the game or stage 1 has run an instruction. **core.s itself is not touched**: its segment has only 10 bytes of room before `hook1`, and the free-RAM pattern gate (`$B8800..`) is not affected (`$DC200` < `$DD000`; the new `used` span is `$dc200-$dc248`).
* It writes `MSTEVAL` (constant in the patch, `3`) to `$FF8E21` iff ALL of: (1) the `_MCH` cookie's high word is 1 (STE hardware family: STE, Mega STE; ST 0, TT 2, Falcon 3; no cookie jar = old TOS = nothing written); (2) a bus-error-guarded byte read of `$FF8E21` answers (vector `$8` is pointed at a handler that resets the stack and returns; restored on both paths; an STE bus-errors there); (3) the byte reads 0. A non-zero value is left alone. The cookie test is an extra guard on top of the bus-error probe so that a TT / Falcon whose `$FF8E21` happens to answer is not touched.
* **0 is "not set yet".** An explicit 8 MHz without cache is also 0 and is raised to 16 MHz as well (lead decision). The user can keep a speed by setting it to anything non-zero before the game (e.g. 16 MHz without cache = 2), otherwise only the v1.1 zips give 8 MHz; there is no way back to 8 MHz while the game runs (the game takes the machine over: no desktop, no control panel).
* Bug found by the first build [obs]: the first version used `a2` freely; core.s's init loop keeps its table pointer in `a2` across the calls (the comment "may use every register" is wrong for `a2`; `hd_core` and `p4_spr` save theirs), so the game jumped to garbage and the machine returned to the desktop (`/tmp/strun-tmdd0hof/shots/grab0073.png`, `16MHz(CE)` in the status line). The routine now saves/restores everything it touches (`movem.l d0-d1/a0-a2`).

## 3. Value: `$02` or `$03` [obs, Mega STE TOS 2.06 4 MB, floppy, map view, 60 Hz]
| register value | cycles/VBL | fps | ticks/s | note |
|---|---:|---:|---:|---|
| 0 (v1.1) | 133581 | 4.50 | 4.016 | 8 MHz |
| `$02` 16 MHz, cache off (`mste_fl_c2.out`) | 267184 | 5.04 | 4.016 | +12 % only |
| `$03` 16 MHz + cache (v1.2 floppy) | 267186 | 8.16 | 4.016 | +81 % |
PMSpeed's 10.18 fps came from `hatari-option --cpuclock 16` (plain 16 MHz CPU, no bus wait states and no cache model). Hatari models the Mega STE's 16 KB cache cycle-exactly (manual: "8/16 MHz CPU speed and cycle accurate external 16 KB cache"): at 16 MHz without cache the RAM accesses wait for the 8 MHz bus, so the cycle counter doubles (the "~266K" gate passes with either value) but the game hardly speeds up. Lead decision B: write `$03`. The README says plainly that the cache is on and unproven on real hardware.

## 6. Stale-cache hazard check: RAM at the same game pass, v1.1 at 8 MHz against v1.2 at 16 MHz + cache [obs, `/tmp/pm16/dig.py` + `cmp.py`, Mega STE floppy]
Method: cold boot to the map view, a debugger breakpoint `($2df70).l = 300` (the main-loop pass counter, cleared at the game start; reached at pass 26-36 on arrival) saves RAM `$0..$FFFFF`; two runs per build. Every run is non-deterministic in a few places (pointer, sound queue, VBL counter), so the same-build pairs are the noise baseline.
| pair | differing bytes below `$B8000` |
|---|---|
| v1.1 a vs v1.1 b (same build, same machine) | 149 (31 spans: low-RAM vectors / sound variables `$465..$fef`, `$1c48e`, `$2c774..$2c9a9`, `$6f307` the VBL counter) |
| v1.2 a vs v1.2 b | 333 (55 spans, the same variable areas plus pointer pixels in the screen buffers `$1d1xx`, `$24fxx`) |
| v1.1 vs v1.2 | 784 (111 spans) |
Outside the 96-byte-dilated union of the two same-build noise sets the v1.1 / v1.2 difference is the same **183 bytes in 24 spans in all four cross pairs**: every one of them lies in a screen buffer (`$1d129-$1d1d6`, `$24ecb-$24ed6`, `$26710-$26855` = buffers A `$1c700` / B `$24400`; `$70acb-$71074` = buffer C `$70000`), 7-14-byte pixel runs (the pointer / drawn frame at the sampling instant; the two builds' pointer sits at another place because the cold-boot navigation is timed in wall time). No difference in the game text, the resources, the tables or the world state beyond the noise areas. This is evidence that the code and data the game loaded and unpacked are the same with the cache on; it cannot prove cache coherence on the real chip: **Hatari models the cache's timing, not stale lines** [INFERENCE: its manual says "cycle accurate external 16 KB cache"; a stale-line model would be a new feature]. The real Mega STE's cache is described as write-through and DMA-aware (TOS and the control panel enable it for all software) [INFERENCE, not checked against hardware documentation].
Note on section 6: that the 183 bytes are the pointer / a drawn frame is [INFERENCE] (they are pixel runs in the screen buffers; not decoded further). **HD (ACSI, same method, `dig_hd_*.out`)**: v1.1 a/b 603 B, v1.2 a/b 312 B (same-build noise), v1.1 vs v1.2: 747 B in 111 spans, of which outside the same-build noise mask only **26 bytes in 4 spans, identical in all three cross pairs, all inside buffer C `$70000-$77CFF`** (`$70acb-$70ad6`, `$72310-$72315`, `$723b0-$723b1`, `$72450-$72455`: pixel runs, the same byte patterns as the floppy's differing runs): the loaded and unpacked code and data are the same with the cache on, floppy and HD.

## 8. What is not proven
* **Real hardware and MiSTer:** none run. Whether `$FF8E21` exists in a MiSTer MegaSTE core (it may bus-error, answer 0, or ignore the write) is unknown: a bus error is skipped by the guard, a read that answers non-zero leaves it alone, a core that answers 0 and ignores the write loses nothing. The speed gain exists only where the register is really implemented.
* **The cache** (the user's expectation of a faster game needs it): Hatari does not model stale cache lines (section 6); the game loads code by floppy DMA / ACSI DMA and rewrites its own instructions at two hand-overs (`$576`, `$10A6`; the 68030 icache failed there on a TT, regression.md). The HAGA loaders of Midwinter / Populous / Moonshine write `$FF` (16 MHz + cache) on the user's image and run (lead's precedent, not re-run here). If the cache misbehaves on a real Mega STE the user sets 16 MHz without cache (any non-zero value) before the game, or uses the v1.1 zips.
* The all-games image with the v1.2 zips and `pmretire.py --img`: the lead's step; here the HD cells are the shipped HD folder on an ACSI disk with HDDRIVER (the image's driver path), not the image.
* `pmtick.py rate` (snapshot-based, fixed STE snapshot, clock set after the start) cannot measure a start-up register; the same fps / ticks figures come from `pmreg.measure` (the sampling `pmtick` uses) on the cold boots of section 4: 4.016 ticks/s, 8.1-8.2 fps at 16 MHz + cache (not the ~10 fps of PMSpeed's `--cpuclock 16`, section 3).

So on that core `$FF8E21` is implemented and the write of `$03` (cache on) works, for the floppy build.
