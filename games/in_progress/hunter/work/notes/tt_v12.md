# Hunter v1.2 on TT and Mega STE: is "4 fps" a regression? (HunterTT)

Tags: **[obs]** raw output of `tools/ttbench.py` (new, mine; logs in /tmp/ttv/logs, Hatari 2.6.1); **[src]** Hatari source `/home/ryan/Code/hatari-pist/src` (a newer fork than the installed 2.6.1: [INFERENCE] that 2.6.1 matches); **[disasm]** `tools/m68dis.py` on `work/dumps/ram_foot_stand.bin`; **[INFERENCE]** unproven.
Tool: `tools/ttbench.py CELL --kind hd|fl --machine tt|megaste|ste|falcon --game DIR | --disk FILE | --image VHD` = run_tt.sh / run_megaste.sh flags (`--cpuclock 32 --monitor vga --mmu true` / `--cpuclock 16`; harness' `--sound off`, `--fast-boot`). Metric: breakpoint on the frame-loop top `$253e` (once per frame, never patched) over 500 emulated VBL -> fps and VBL/frame; `PROFILE` = Hatari cycles per VBL by region (idle = frame-wait spin `$aaa2-$aabd`); `SPEED` = fast-forward, VBL per host second (host cost); CACR from the debugger `r` (`$ff8e21` on the Mega STE). "stand" = HQ at the mission start, "walk" = Up held. Builds: the three release zips (v1.0/v1.1/v1.2, HD and floppy), PP's original HD game (`_MCH` poke), minus-group builds from `huntpatch.py build --only`.

## 0. Verdict
1. **No v1.2 regression exists on the TT or the Mega STE [obs].** On the Mega STE (16 MHz, cache on) v1.2 is *faster* than v1.1 (8.8 vs 8.4 fps standing, 15.8-16.0 vs 14.1 walking). On the TT v1.0, v1.1, v1.2 and PP's original all run the HQ at **50 fps = 1 VBL/frame** (the 50 Hz cap), HD and floppy, with the data cache on (HD) - so "4 fps" is not the emulated frame rate of the 3D view on any build.
2. **What gives 4-10 fps on a TT is the Demo, not the game** [obs + disasm]: my first floppy runs used fixed-wait navigation, which landed in the main menu's Demo (screenshot `blind_scene.png`: "You have boarded a car", position moving at 240-545 u/s with no input). There 90 % of all cycles are the replay's schedule spin `$5f7e` (`cmp.w $1a8(a5),d0 / bgt.b $5f7e` in `$5f6a`, the scripted path `$95` bit 7): the Demo replays at its recorded pace (8.1 VBL/frame = 6 fps; 4.4-5.5 with the data cache on) whatever the CPU. That fits "about 4 fps on a TT and on a Mega STE alike" [INFERENCE: I do not know what the user watched; the title does NOT start the demo by itself, 227 s waited, `exp_attract`]. **Ask the user: Demo, or Start new game?** The other candidate is host speed (section 4): this host runs the TT cell at only 0.92-1.5x real time at fast-forward.
3. **One real inefficiency found and fixed: the floppy build ran the 68030 with the data cache OFF** (`core_floppy.s` stage 1 `moveq #1,d2 / bsr ccache`, stage 2 never turned it on). It is in v1.0, v1.1 and v1.2 floppy, not new. Fix: patch `fdc_dma` (below). Measured: TT floppy HQ stand idle 2 % -> 7 % (same as HD), **Falcon floppy 21.6/25.3 -> 25.1/28.3-29.2 fps (+16 %/+13 %)**; TT stays 50 (cap).
4. Not a regression but TT-specific: the p4 patches (68000-tuned) cost the TT about +14 % busy cycles at the HQ versus PP's original (section 3); the p4-off TT cells did not finish in this run.

## 2. The fix: `patches/fdc_dma.s` (+ `core_floppy.s` stage 2, `huntpatch.py`)
Mechanism [disasm `ram_tail_floppy_1mb.bin`]: the Paper Bag loader reads sectors by FDC DMA straight into the destination (`$d4b6..$d4ec`), then waits in `$d50e bsr.b $d51c / $d510 add.b d3,d6 / $d512 tst.b d3`. A 68030 does not snoop DMA and the loader never flushes, so stage 1 switched the data cache off (`core_floppy.s: andi.w #$feff,d0`) and stage 2 left it off.
Change: site `$d50e` (6 bytes `610cdc034a03`) -> `jsr $8d360.l`; the blob runs the displaced three instructions in the same order, and when FLAGS bit 4 is set clears the data cache (`movec cacr`, `ori.w #$0800`) after every FDC command (the way TOS's drivers do), d0 preserved. Stage 2 (68020/030 only, only when every site was applied AND `$d50e` holds the `jsr`) sets FLAGS bit 4 and turns ED back on (`ccache` d2.b = 2). 68000/68010 and 68040/060: unchanged. `huntpatch.py`: new header `; floppyonly: yes` (HD build skips it), prefix window `fdc_` = `$8D360-$8D3FF`. `core.s` header documents FLAGS bit 4. `patches/README.md` (lead-owned) still needs a row for `fdc_dma`; FLOPPY.TXT still says the TT was tested with HD only.
Gates [obs]:
- HD build byte-identical: `md5sum build FILES/P 4c71c6cf...` and `START.TOS 28c613b4...` equal to the v1.2 release (HD huntab therefore identical by construction). `huntpatch.py verify` and `verify --floppy`: ALL OK (`fdc_dma site $0d50e ... tail dump 610cdc034a03 (match)`).
- STE floppy: RAM dumps after the cold boot, fdc_dma vs v1.2: hook bytes `4eb90008d360` at `$d50e`, blob at `$8d360`, FLAGS `00000003` (bit 4 clear), 3D view reached, fps 5.0/9.5 vs 5.0/9.3. (The two dumps are taken at different game moments, so a whole-RAM diff is noise; the code-side differences are exactly the hook and the stage-2 bytes, `stage_len` 538 -> 588.)
- TT floppy: `FLAGS=00000013 CACR=00003111`, 3D view reached, 50 fps; the hook ran 389-397 times between the loader's start and the 3D view (`--hook-hits`: breakpoint `pc=$8d360`, 390 and 398 hits incl. the one START_PC hit). Falcon floppy FLAGS `1b`, CACR 3111, reached the 3D view.
- Negative/guard: a build without `fdc_dma` keeps CACR 3011 and FLAGS 03 (`tt_fl_nofdc`). Control: data cache on without the flush (`tt_fl_ctl`) loads fine in Hatari too: **Hatari does not model the stale-DMA hazard, so the flush is not provable here [INFERENCE: real hardware]**; the hook is there for that case. `patches/fdc_dma.s` is `default: yes`: flip it to `no` if the lead wants no unprovable code (stage 2 then leaves the cache off by itself).
- Harness note: fixed-wait ("blind") navigation of the floppy cells lands in the Demo and must not be used for fps (my first TT/Falcon floppy numbers, 4.9-8.7 fps, were the Demo); `ttbench.py` now navigates by crops (`TTBLIND=1` for the old way).

## 3. TT-specific cost of the p4 patches [obs, partial]
PP original idle at the HQ 85,673 of 453,592 VBL cycles (stand) / 262,135 (walk); v1.0-v1.2 idle 33 k / 240 k: +14 % / +11 % busy cycles on the TT for the same picture (payload bucket 190 k cycles/VBL standing). The 68000-tuned `p4_poly`/`p4_edge`/`p4_ikbd` are the only code that differs there ([INFERENCE]: the cells that would prove it, TT HD minus p4_*, did not finish; builds are in /tmp/ttv/m_p4*). Gating `p4_` off on 68020+ (restore the originals as `jag_pad` does) would give the TT +11-14 % headroom; only visible where a frame exceeds 1 VBL.

## 4. Why I cannot reproduce "4 fps"
HD all-games image on the TT (run_tt.sh flags): 49.5/50.1 fps, CACR 3111; on the Mega STE 8.8/14.8, `$ff8e21=ff`. Hatari ran those at 0.93x real time (pacing). The same host's maximum speed (fast-forward) is only 1.07-1.5x real time on the TT with the MMU and 4.3-5.5x on an STE: a host a few times slower than this one (it was at load ~10) would show the TT at a fraction of 50 fps **for every build including PP's original** ([INFERENCE]). Two things the user can check: does the title/menu animation also look like ~4 fps (host or display), and is it the Demo.

## 5. Part 2: what the TT can get (no implementation, awaiting approval)
**Triple buffering.** Evidence: forcing `tb` on (poke `TBON` `$8c1b6` = 1) on a TT at `--cpuclock 8` [obs, `exp_tb`]: off 12.6 fps (3.96 VBL/frame) standing, 16.8 walking; on **22.5 (2.22) standing, 31.4 (1.59) walking**, game kept running, no tearing visible in six screenshots (`tb_sheet.png`; scenes not identical). At 32 MHz there is nothing to gain: the heaviest sampled view (HQ stand) needs 0.93 VBL and is capped at 50, so tb only pays on slower TT/Falcon settings (Falcon floppy 2 VBL/frame, 16 MHz TT) [INFERENCE for the Falcon]. Mechanism for the base: `Video_GetScreenBaseAddr`/`Video_RestartVideoCounter` [src] latch `VideoBase` at the frame restart, but Powermonger/MW2 notes (`tt_ptr`) observed Hatari's TT/Falcon following the register at once; on a real TT the latch is [INFERENCE] unknown. Safe design (the tt_ptr idea): `tbf` stores the finished page in a variable and `tb_vbl` (already runs first in every VBL) writes `$ff8201/03` from it, rotating three pages so the shown page is never drawn; the pointer code (`$a65c`, later in the handler) then draws into the page about to be shown. Effort: small-medium (one new state word, `tb_vbl` writes the base, remove the 68020 gate, gates = the existing hunttb_ab/pointer checks on TT). Risk: on a 68000 the base written in the VBL handler is latched one frame later than a mid-frame write (so keep the 68000 path as is); real-TT latch timing untestable. Worth it only below 1 VBL/frame headroom.
**Sky.** Hatari's TT video renders ONE palette per frame: `Video_RenderTTScreen` -> `Screen_GenDraw(VideoBase, ...)` once, `Video_TT_RasterHBL` only updates the video counter ("assumes the TT screen is using the same display mode during the whole frame") [src]. Experiment [obs, `exp_sky`]: poking the sky state `V_ST` (`$8eceb`) to 1 on the TT makes `sky_vbl` run its Timer B count: it ended `V_ST = $7f` (**Hatari's TT counts exactly 200 Timer B events per frame**, `IERA=01`, vector `$120` = the sky handler, horizon `$32`), the game kept running, and the screenshot shows **no bands** (sky and sea in the frame-end colour 15). So palette rasters cannot be seen, hence cannot be tested, on a Hatari TT; on real hardware they may work ([INFERENCE]; TT palette bank select `$ff8263` would even make a band change one byte write). Frame-buffer gradient: impossible without more palette entries (all 16 indices are used by the 3D palette; a TT 8-plane mode would mean a new picture format). Effort: removing the CPU gate is trivial, verifying it is impossible here; a framebuffer gradient is a rewrite (XL). Recommendation: leave the TT sky off.
**Amiga dashboard.** Same limit (needs the 16-colour panel palette change at row 139). Without rasters the art can still come: remap the Amiga panel bitmap to the game's own 16 colours at pack time (nearest colour; map `[0,2,3,4,15,5,5,7,7,11,10,0,2,2,12,12]`, preview `work/shots/tt_panel_remap.png`: green Amiga layout, not Amiga colours; it dims with the night palette like the original). Effort: medium (`pnl_data.py` remap, a TT path in `sky2_pnl` that does not need `V_ST`, a CPU gate), risk: the look needs the user's approval, the colours are not the Amiga's.
