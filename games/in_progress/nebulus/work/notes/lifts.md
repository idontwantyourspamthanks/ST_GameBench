## 1. Answer in one paragraph
**A lift is not a creature and has no table of its own. It is three cell values in ONE column of the tower grid (the game's own mask+stream cells)**: a **start slab `$85`** at the lower row, an **end marker `$08`** (bit 7 clear, so non-terrain/invisible) at the higher row, optional **stop markers `$0c`** in between, and (always, 145 of 145) a ledge cell `$81` right under the slab. Walking onto the slab and pressing **Up** starts a ride (player state 6, `$3a3e6`): the frog rises 1 y-unit (= 1/4 row) per game loop; the cells it passes are rewritten into a "stem" (`$80`) and the end marker becomes the platform `$89`; after 125 loops (about 6 s) the platform walks back down by itself (the frog rides down with it) through a 4-slot return queue (`$339ee`), restoring the markers. The data therefore lives **entirely in the existing `NCMP` v1 grid: no format change, no version bump, no decode hook**. The shipped game has **145 lifts in 16 towers (6..14 per tower)**; the level editor currently offers `$85` as "Pale block" (a lone lift start with no end: a trap, see section 6).
The eye discs (`$40/$50/$60/$70`, creature kinds 8/9) are separate enemies, not lifts [disasm `$37a40/$37a60`, `$3b5be`].

## 2. Encoding table
| Cell | Meaning (as read by the lift code) | Where used |
|---|---|---|
| `$85` (`1000 0101`) | **lift start slab** = rest position. Terrain, drawn as the pale cream slab. `v & $0c = 4` marks the bottom. Standing on it (cell directly under the frog's row) + joystick **Up** (`$338f4 = +1`) = ride up. `sub_03ab10` returns d0 = +1 for `$85` [`$3ab14..$3ab34`]. | 145 shipped |
| `$08` (`0000 1000`) | **lift end marker**, non-terrain. `v & $0c = 8`. A ride going up **ends** when the cell under the frog has `&$0c == 8` [`$3a4aa cmp.b #8 / beq $3a4d0`]; the cell becomes `$89` (pale slab, "top platform"), `$89` -> d0 = -1 (rides down on Down) | 144 shipped (every `$08` is the end of exactly one lift) |
| `$0c` | **stop** (`&$0c == $c`): the ride stops here unless the joystick keeps pushing in the ride direction [`$3a4b2..$3a4c4`: up ride continues only while `$338f4 > 0`, down ride only while `< 0`]; the cell becomes `$8d` (platform both ways, d0 = 0) | 12 shipped: 11 as intermediate stop, 1 (M2 T1 col 4) as the only marker = end |
| `$04` | bottom stop for a ride DOWN (`&$0c == 4` ends a down ride [`$3a486`]); a down ride ends by writing `$04|$81 = $85` back | never in shipped data (the original `$85` is turned into `$84` by the up ride and restored to `$85`) |
| `$89` / `$8d` | platform cells that exist only at run time (top platform / stop platform / the walking-back platform). Placed in a level by hand they are down-ride starts (Down on them) | never in shipped data |
| anything in the shaft | the ride reads only `v & $0c` of the cells between; `$80`/`$82` (solid pillar, blue block) **stop the ride** (collision, frog hurt); doors `$83` do not; every cell passed is **overwritten** with `(v&$0c)|$80` and erased (`&$0c`) when the platform returns, so ledge pieces, doors, enemy markers in the shaft are lost after the first ride | |
Fields: **column** (0..15, the shaft is strictly vertical in this column), **start row** = row of `$85`, **end row** = row of `$08` (>= start+1; shipped lengths 1..25, mean 9.3), stops = rows of `$0c` in between. Direction up only from `$85` (down is the player's own Down on the top platform, or the automatic return). Speed fixed: 1 y-unit per loop (`$3a3c8` = +-1, set at `$39ddc: move.w $338f4,d0 / bra $3a3ca (= move.w d0,$3a3c8.l)`), return delay fixed 125 loops (`$3787e move.w #$7d,0(a1)`), return speed 1 row per loop; not per-lift data.

Constraints seen in the 145 shipped lifts [obs, `lifts_scan.py` / stats script]:
- cell under the slab (row-1) = `$81` in **145/145**; one of the two neighbours at row-1 is also a ledge in 106/145 (the frog walks onto the slab from a ledge; the other 39 are reached otherwise);
- end marker sits in the row of a ledge, at least one horizontal neighbour is a ledge in 111/145 (frog steps off); 34 end at doors/open air;
- several lifts per column are normal (M1 T1 col 14: rows 10..14 and 20..29; `$85` never inside another shaft);
- the shaft contains `$82` blue blocks in 40 lifts (57 cells; the frog must shoot them before the ride), `$91` crumble ledge pieces in 16 lifts (35 cells), enemy markers in 9 lifts (11 cells);
- `$08` on the same cell as other bits: an enemy marker must keep bits 2-3 clear (`$10..$71` do), or the ride reads it as a marker.
Per tower (M1 T1..T8 | M2 T1..T8): 6 9 6 7 10 11 14 9 | 6 6 8 11 10 9 14 9 = 145. Engine limit on simultaneously returning platforms: 4 (`$339ee`, 4 x 10 bytes: `+0` timer/`$ffff` free, `+2` cell address, `+6` saved cell; reset by `$3783a` at level start `$3dc18`/`$3de32`); data limit: none.

## 3. Ride mechanics [disasm]
- Start `$39dc4..$39ddc` (player state 0, joystick vertical): `bsr $3ab10` (a0 = cell under the frog = grid + (x>>3)*256 + (y>>2) - 1; `$85 -> d0 = +1`, `$89 -> -1`, `$8d -> 0`; carry set) ; start if `d0 == 0 || d0 == dy` -> `$3a3ca` stores dy in `$3a3c8`, `a1e = 0`, state 6; `bsr $3ab10 / bra $378fc` cancels a pending return of this cell.
- State 6 `$3a3e6`: first centres x on the column (`x & 7 -> 4`, 1 px per loop), then `$3a41e..$3a444` sets `$3390a = $25` (draw the stem under the frog; `$ffff` otherwise, `$39352 tst.w $3390a`) and rewrites the cell under: `(v & $0c) | $80` going up, `v & $0c` going down. Then y += dy each loop; every 4 units (`y & 3 == 0`) the next cell: up: `&$0c == 8` -> end, `== $0c` -> end unless Up held, else write `(v&$0c)|$80`; down: `&$0c == 4` -> end, `== $0c` -> end unless Down held, else write `v&$0c`.
- End `$3a4d0`: `ori #$81` -> cell `$89`/`$8d`/`$85`, `bsr $37854` (queue the return: `a1 = $339ee` free slot, `saved = *cell`, timer `$7d`, only if `saved & $0c != 4`), `$3390a = -1`, state 0.
- Return `sub_037898` (called every game loop from `$3ddc8`): timer to 0, then per loop: `*cell = saved & $0c` (restore `$08`), cell-1, `saved = *cell`; `&$0c == 4` -> `$85` and slot freed, else `$8d` (the platform the frog stands on walks down).
- Abort `sub_03a572 ... $3a5ca`: while in state 6 the frog position is tested with the terrain collision `sub_03a7ce`; a hit at `y & 3 == 0` goes `$3a64e: sub_03ab10 / sub_037854` (platform queued back) and state 7 (hurt, then fall/death: -1 life) [obs below].
- Class table `$315e0` (`$38028`): `$85` has `v&3 = 1`, `v & $0c = 4` -> class 20 (the "pale slab" class); `$84/$88/$8c` (ride cells) class 10.

## 5. Where it lives in the packed data
Same place as every cell: tower stream byte of that (angle, row) (see level.md section 4). Value-only edits (cell already in the stream) work with `nebedit.py set`: tower 1 lift col 6 `$85` = `$43c1e` (`U$1011e`), `$08` end = `$43c23` (`U$10123`); lift col 12: slab `$43c2a`, end `$43c34` (`U$10134`), the ledge cell (12,14) `$43c3c` is `$81`, so "extend the (12,5) lift to row 14" = `00` at `$43c34` and `08` at `$43c3c`. Moving an end to a row that has no stream byte needs the structural re-encode (mask bit + stream byte): exactly what the editor's record does (`ovl.encode`), so nothing extra for lifts. Lift cells are plain cells: copy/import (`import-original`) already carry them.

## 6. Editor design (cell menu flow, no format change)
**Format: unchanged.** `NCMP` v1 level record = mission, base tower, rows, flags, len, time, name, mask+stream; the lift is three cell values in the grid, so nothing is added, `version` stays 1, no trailer, no loader/validator change, the 8 KB budget only pays the 3-4 stream bytes per lift. Playtest uses the same working grid; the game rebuilds its own return queue at every level/life start (`$3783a` at `$3dc18`, `$3de32`), so **no hook in the decode path (`$377a2`) is needed**: [obs run 3: the lift works from the overlay record exactly as from the original data].
UI (code in `work/lifts/ed_lift.s`; **built into a private copy of the editor by `work/lifts/build_lift_editor.py` and exercised in Hatari**, section 6b):
1. Root menu: **replace `Pale block` (`$85`) by `Lift >`** (the stand-alone `$85` is not a block: it is a lift start with no end, the ride then only ends by hitting terrain and hurts the frog; editor.md sections 3.4/7 that call `$85/$89/$8d` "solid" are wrong).
2. `Lift >`: `Lift: from here` / `Lift: stop here` (`$0c`) / `Lift: delete` / `< back`.
3. `Lift: from here`: writes `$85` at the cursor, then arms the pick mode (`vLift = row+1`): status line "Lift: U/D = other end", the cursor is locked to this column (left/right ignored), **Fire = the other end**: above the start -> `$08` there; below -> the lower row becomes the slab, the first cell becomes `$08` (so the user may pick either end first); same row -> "Pick another row". When the second end is set the editor puts a ledge `$81` under the slab if that cell is empty (all shipped lifts have it). F10 cancels the pending pick (the lone slab stays; `Lift: delete` removes it). On a cell that already is a lift slab the command first erases the old `$08`/`$0c` above it = "move the end". `Lift: delete` works with the cursor on the slab, in the shaft or on the end/stop marker of the lift (never reaches a different lift: the search down the column stops at another lift's `$08`).
4. Warnings (status line, same mechanism as "No ledge below!"): `Pillar blocks lift` (a `$80` between slab and end). Offline tool (`ovl.py` patch below) also reports: no end marker; `$82` blue block (note: the frog must shoot it); bits 2-3 on other shaft cells; another start inside the shaft; no ledge under the slab; no terrain beside start or end; orphan `$08/$0c`. Over the 145 shipped lifts the rules give 0 warnings (only notes), so they do not cry wolf.
5. Display: tile 6 (`$85`) renamed "Lift start" (pale slab); two new 8x8 tiles 17 (`$08` end, arrow) and 18 (`$0c` stop, arrow + bar) so the end is visible instead of the invisible dot of "Marker (inert)"; `classify` returns them for non-terrain cells with `k == 0` and `&$0c` = 8/$c.

## 9. User-guide text to add (editor.md section 9)
`Lift >` : "Lift: from here" puts a lift platform (and a ledge under it) at the cursor, then move the cursor up or down the same column and press fire where the lift should end (a marker is placed; F10 cancels).
