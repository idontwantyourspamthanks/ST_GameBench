# Moonshine Racers patches — format, boot mechanism and address map

Tool: `python3 tools/msrpatch.py list | verify | build | live | version | doc`. Design copied from Midwinter 2 (`mw2patch.py`) and
Populous 2 (`pop2patch.py`), re-derived for PP's Moonshine Racers HAGA conversion. Evidence (disassembly, hook instants, boot logs) is in
`work/notes/delivery.md`.

## Patch format (`patches/*.s`, vasm mot syntax)
Header comment lines before the first `org`; then one code segment per `org`:
`; name: X` · `; default: no|yes` (default yes) · `; site: $addr` (RAM site, required for a RAM patch) ·
`; orig: <hex>` (expected original bytes; optional, the tool derives them from the RAM dump and cross-checks both dumps) ·
`; phase: boot|stage1` (default `boot`: every patch site is loaded when the trampoline runs; `stage1` = the site lies in the stage-1 LOADER (`MSR_S1.FIC` unpacked at `$78000`, which runs BEFORE the trampoline: it draws the "Moonshine Racers" title picture and loads the game): needs `; site:` in `$78000-$7E3FF` and `; orig:` (checked against the unpacked `MSR_S1.FIC` and, with the STX images, disk A); HD: RUNME's copy routine verifies/applies the site right after the payload copy (all or nothing), floppy: the same bytes as a disk A edit of the stage-1 sectors (tracks 1.. side 0, in RAM order, a site must not cross a track); never part of `live`; blobs of such a patch live in the payload as usual (already in RAM, the font and the game are NOT) ·
`; data: $addr len [free]` (zero-initialised blob-owned data, repeatable; `free` = outside the payload image, not zeroed) ·
`; media: floppy` (built only by `build --floppy`, `work/notes/floppy.md`; a `--only` list for the HD build refuses it) · `; disk: A|B $offset <orig hex>` (floppy disk patch: an edit of the .ST image at that file offset, no `; site:`; the segment whose `org` equals the offset gives the new bytes, same length; `build --floppy` and `verify` check the original bytes in the STX conversion; repeatable) · `; note: ...` (repeatable) · `; doc: ...` (one line for PATCHES.TXT).
`; ram: $lo-$hi [label]` (RESERVED run-time work RAM, inclusive end, repeatable: NOT part of the payload image and not zeroed by it, so it does not count against `IMG_MAX_LEN`; the tool still checks it like a blob: it must lie inside the free run of every layout the build supports (1 MB; 4 MB only with `pp_bigram_cache` or in the floppy build; a HD build without that file patch is refused), must not overlap any other patch's site/blob/data/ram or the site table (`verify` pairs every patch with every other; `build` the selection), and `verify` demands that it is zero in the stock game's RAM dumps (hook instant, entry, three race dumps)) ·
`; requires: A B ...` / `; conflicts: A B ...` (patch dependencies: `build`/`live` (also `--only`), the default selection and `verify` refuse a selection that lacks a required patch or holds a conflicting one, with a message naming both; unknown names are an error; a pair of patches whose footprints overlap must declare `conflicts`, `verify` refuses undeclared overlaps).
Equates (`NAME equ value`) may precede the first `org`. The tool predefines `IB` (payload image base `$B2700`) and `TABLE` (site table `$B7000`).
The segment whose `org` equals the site gives the NEW bytes (at most the orig length, nop-padded). Every other segment is a BLOB at a fixed
absolute org inside a blob area (below). `org` takes `$B2800` or `IB+$100`.
`@VERSION@` in any source (and in docs, via `msrpatch.py doc FILE`) is replaced by the release version; the token `{PATCHES}` in a doc expands to
the default patch list, `{RAM}` to the payload/reserved-RAM map of the default set (the same map is the tail of `msrpatch.py list`).

File patch (PP's resident loader HAGA, `; image: HAGA`): `; edit: <HAGA file offset> <expected original hex>` (repeatable) and one segment
`org HB+$<offset>` per edit with the same length (HB = the RAM base of HAGA: `$F8000` 1 MB, `$1F8000` 2 MB, `$3F8000` 4 MB+; used only for
pc-relative references: `verify` assembles at the three bases and demands identical bytes). `build` refuses to apply over different bytes.
File patches are not applicable to `live` (HAGA is already resident in a snapshot).

## Where the game is delivered, and what runs when (details with disassembly: `work/notes/delivery.md`)
`RUNME.TOS` (shipped unpacked and edited at two points; `pp_depack` unpacks PP's LZ):
1. **Staging.** The stack-phase block (RUNME text `$352`-`$ad1`, copied by PP to `a3 = $B1F44` at 1 MB) ends the stage phase with
   `jmp $78000.l` (text `$3b4`, RAM `$B1FA6`; `$78000` = PP's stage 1 `MSR_S1.FIC`, unpacked). That `jmp` becomes `jmp copy.l` into a copy
   routine appended to RUNME's data segment, which copies the **payload image** (appended after it) to `IB = $B2700` and continues with the displaced
   `jmp $78000.l` (registers and SR preserved). The disk loads that follow (stage 1 and the game from MS1/MS2) never touch RUNME's TPA data
   before this point, and `$B2700` is above PP's chunk cache (`$81000-$B1D40`) and the stack-phase copy (`$B1F44-$B26C3`).
2. **Trampoline.** PP's patcher ends with `jmp $1000.w` (text `$45c`, RAM `$B204E`, 4 bytes + 2 zero padding bytes) — after PP's last RAM patch,
   right before the game starts (`$1000` = `bra.w $6f50`). It becomes `jmp $B2708.l`. The trampoline (`core.s`) runs in supervisor mode, IPL 3, with
   all of the game loaded: it VERIFIES every site's original bytes, APPLIES all or nothing, writes the marker, flushes the 68020+ caches and ends with
   `jmp $1000.w`.
3. **RUNME relocation.** Growing the data segment by N bytes moves the bss: the header data length, every relocated long that addresses the bss (>= text
   `$4446`) and the reloc table (re-encoded, round-trip checked) are adjusted; the four `lea d(pc),aN` that address the bss (text `$98`, `$b34`, `$40fa`,
   `$410c`) cannot span the payload as 16-bit displacements, so each becomes `movea.l d(pc),aN` (same 4 bytes, same register, no flags) reading
   a relocated pointer from two slots behind the copy routine. `verify` scans the whole text for any other `d16(pc)` operand that reaches the bss.

Marker at `$B2700`: `MSPO` = all sites applied, `MSPF` = a mismatch, nothing applied, zero = the trampoline never ran. A zero-patch build behaves like PP's
build plus the staging and the marker (**not pristine**: it still contains the staging, the HAGA file patches and the changed RUNME).

Image limit `IMG_MAX_LEN = $F000` (61,440 B: `$B2700-$C16FF`): RUNME refuses to start ("Too much low RAM occupied") when its bss start + `$8000` reaches
`$38270` on a 1 MB machine (RUNME text `$98-$c8`; `lea $4666(pc),a1` + `adda.l #$8000`). Measured headroom and the capacity test: `work/notes/delivery.md` section 6.
`; data: ... free` reservations outside the image are not zeroed: initialise them lazily behind a magic long (rendering.md shows `$B2700-$E8400` zero at
game start on 1 MB, but not at 4 MB without `pp_bigram_cache`).

## Patches
- `pp_bigram_cache` (HAGA file patch, `default: yes`): PP's loader switches to a "whole image" disk cache on 68000 machines with >= 4 MB (`$81000-$C6F2B` for MS1,
  `$81000-$13D7FF` for MS2), which overwrites the payload. The patch keeps the 1 MB chunk cache (identical to Midwinter 2's patch; same HAGA md5).
- `mr_edge` (`default: yes`), `mr_map`, `mr_digit` (`default: no` since `hd_stage`: the minimap kernel and the score-digit kernel are only reached through routines the new HUD no longer calls; files kept) (pixel-identical render patches, `work/notes/render_patches.md`): `mr_edge` the road edge-colour routine `$1058a` (one of 8 generated code slots per frame), `mr_map` the minimap draw `$12690` (unrolled row loops), `mr_digit` the HUD score-digit kernel `$14d98`. `mr_negctl` (`default: no`) is the gate negative control (breaks the edge colours on purpose).
- `hd_stage`, `hd_init`, `hd_clouds` (`default: yes` except `hd_init`, which is `default: no` since the tightening integration: the default set uses `ta_init` instead, same site `$edea`, same work plus the face-shadow reset; `hd_init` stays for a set without `ta_erase`; VISIBLE change, `work/notes/hud_build.md`, design `work/notes/hud_design.md` layout A): the new top-bar HUD and no clouds. `hd_stage` (site `$ef7a`, the HUD stage called once per pass from `$7b4c`; blob `$BB000`, generated by `tools/msrhudgen.py`, do not edit `hd_stage.s` by hand) replaces
  the thirteen stock HUD calls and the cloud erase/draw by one 16-row black strip with score, clock dial, race position `#`, speed `MPH` (high word of `$10d8`, 128 with turbo), gear `G` (1/2), engine temperature `T` (hot colour from 28) and the turbo gauge (cup icon + 28-pixel bar); it keeps the message ticker `$11ef0` (its state machine gates the race end),
  the face `$f90c` and the hit/sound part of the old cup routine (`$11ce` -> sound `$36`, `$11cf` slosh counter evolve exactly as stock). Every field is compared with a per-buffer shadow (`$BCF00` for `$70000`, `$BCF40` for `$78000`) and redrawn only when it differs from what THAT buffer shows. The first pass into a buffer after the race init paints the strip and the
  sky (all planes set) over rows 16-64; `hd_init` (site `$edea`, replaces the cloud init `$dd18`) clears the shadows' `painted` bytes at every race start/restart. `hd_clouds` (site `$7b3a`) removes the cloud position update `$dd50`. Palette A colour 14 (`$3cf0`) is set to `$777` every pass: white text. The occupancy map `$6f000-$6ffff` has no reader any more
  (its only readers were the cloud passes): face and message path still write it (dead work, kept: shared kernels), proof `hud_build.md` section 6. `hd_init` requires `hd_stage`; the pacers `mg_sync`, `mx_sync`, `mf_sync` require `hd_stage` (their extra frames call TOPBAR `$BB000`, the ticker with saved state and the face).
- **Tightening wave (all pixel-identical, per-pass game state identical to stock, `work/notes/{tighten_a,tighten_b,tighten_c,integration}.md`; default since the integration):**
  - `ta_erase`, `ta_init`, `ta_facestat`, `ta_glyph`, `ta_ymw` (speech/ticker/YM; `ta_face` is the pixel-identical option): `ta_erase` (site `$1209c`) the 49-row message-box restore as two `movem.l` per row (-24 k on each of the 2 erase passes of a message) and owner of the face-shadow words `$BEF00`; `ta_init` (site `$edea`) **replaces `hd_init`** (declared `conflicts: hd_init`; `hd_init` is `default: no` now, the option for a set without `ta_erase`): the same work (clears the `painted` bytes) plus forgetting the face shadows; `ta_facestat` (site `$f994`; **VISIBLE, `default: yes` since the final integration, user-approved**) draws the talking face ONCE per message and buffer with the mouth frame of the message's first pass, so the mouth does not move while a message is typed or held (-6.6 k per message pass; only mouth/eye pixels of the face box differ from the stock game); `ta_face` (same site, `conflicts: ta_facestat`, `default: no`, pixel-identical to stock) draws the face only when the sprite index differs from what that buffer shows (-4.4 k per message pass); `ta_glyph` (site `$14fd4`) MOVEP glyph kernel (-1.2 k per message pass; MOVEP: 68000-68030); `ta_ymw` (site `$8e2c`) skips YM register writes whose value did not change (-1.4 k; identical chip state).
  - `tc_clr`, `tc_proj`, `tc_dist`, `tc_hit1`, `tc_hit2`, `tc_ord` (logic stage, blobs `$B6800-$B6FFF`, one data word `$B6FF0`): `tc_clr` (site `$17c24`) the EXACT span-buffer clear (zeroes only what the previous geometry run wrote: memory afterwards identical to stock, so no state-gate mask on the road-geometry region is needed; `-1.9 k`), `tc_proj` (`$e316`, -1.9 k), `tc_dist` (`$e2e8`, -1.1 k), `tc_hit1` (`$18bf4`, -0.5 k), `tc_hit2` (`$18c86`, -0.9 k), `tc_ord` (`$e406` object stage entry, -1.2 k). `tc_clrx` (`default: no`, `conflicts: tc_clr`) is the faster (-4.3 k) but not state-exact variant (needs the named gate mask TC_GEOM).
  - `tb_car` + `tb_carph` (sites `$39ac` kernel-table long, `$ed90`; blobs `$BF500 $BFC00`, data `$BF000-$BF4FF`, reserved RAM `$D8000-$E2BFF`): the player car and its second layer are drawn by straight-line code generated at run time from the bitmap (about 10 k cycles instead of 33-36 k per draw), cached per (bitmap, rows, x shift, wheel-animation state) in a 40-entry table and a **44,032 B code pool** (`$D8000-$E2BFF`, the whole free range up to the TOS 2.06 1 MB ceiling; it was 24 KB before the integration). `tb_carph` keeps the wheel-animation state label. **Machines: the generated path runs only on a plain 68000 without the Mega STE register `$ff8e21` (ST, STE); Mega STE (16 MHz + cache), TT, Falcon and 68010+ always use the stock kernel** (generated code is never executed where a CPU cache exists). Gain at 8 MHz STE: -40 k per pass driving straight, -30 k with constant steering (pool-size sweep in `integration.md`).
  - **Timer-B and risk items, `default: yes` since the final integration (each user-approved, each has an off switch in `tools/play.sh`; `work/notes/integration.md` section 12):** `ta_rb`, `ta_rb0` (Timer B list: the interrupts that rewrite the sky colour already on screen are dropped; the same colour on every scanline and the same palette switch, proven in Hatari's palette-write trace over a 6,000-VBL steered drive - `--no-rb`; raster timing on real hardware unproven, -4.9 k per pass); `ta_nomouse` (drops the IKBD mouse query while `$1021 == 2`, i.e. in the race; the race never reads the mouse variables, menus keep the query - `--no-nomouse`; -8.2 k); `tb_blit tb_blit11 tb_blit13 tb_blit15` (STE blitter for the big shifted 1-3 column sprites, Timer-B guarded so a burst never starts closer than 2 scanlines to the next raster interrupt; no blitter, Mega STE, TT, Falcon, 68010+ use the stock kernels; `--no-blit`; -9.7 k = 0.06 VBL, the item with the least hardware margin); `ta_facestat` (VISIBLE: the face is drawn once per message, the mouth does not move; `--no-facestat` uses `ta_face` instead; only pixels inside the face sprite box x 272-303 y 17-64 can differ, -1.4 k). Options still `default: no`: `ta_face` (the pixel-identical face optimisation), `tc_clrx` (faster but not state-exact road clear), `hd_init`, `mr_map mr_digit mr_negctl`, `sb_*`, `test_*`, `mx_sync + mx_pre`, `mf_sync + mf_pre`, `mt_sync` (pacers: `play.sh --noextrap` uses `mt_sync`).
- `sb_bar`, `sb_face` (or the option `sb_facestat`), `sb_glyph`, `sb_erase` (`default: no`, VISIBLE, generated by `work/speechbar/gen_sb.py`, `work/notes/speechbar.md`): the speech bar. The message text (2 lines, game font) and the talking face (16x24) are drawn into a permanent black strip, rows 16-41, under the top bar instead of into the sky; drawn on change per buffer (shadow at `$BA900`), the ticker state machine and the face state machine run as stock (hooks `$f90c`, `$f994`, `$120a4` -> `rts`, `$12086` -> `rts`). Replaces `ta_face ta_glyph ta_erase ta_init` (declared conflicts; use `hd_init`); also conflicts `mr_map mr_digit tb_blit*` (blob addresses). About 2.9 k cycles per typing pass instead of 8.4 k with `ta_*`.
- `test_hdref` (`default: no`, gate reference only, conflicts `hd_stage hd_init`): the stock stage reduced to ticker + face; with `hd_clouds` it draws "the stock game minus HUD and clouds", the reference of `tools/msrmask.py`.
- `rd_geom`, `rd_draw`, `rd_init` (`default: yes`, `work/notes/road.md`, `work/notes/integration.md`): the faster road, pixel-identical. `rd_geom` replaces the road geometry `$100b4` (blob `$B4000`; entry for the pass `$B4004`, pre-warm entry `$B4000`),
  `rd_draw` the span draw `$17c42` (blob `$B5000`; pass entry `$B5004`, pre-warm entry `$B5000`). Together -67 k cycles per driving pass (-8.9 %) and -123 k standing (-17.5 %) on top of `mr_*`. They need free RAM `$C0000-$CAFFF` / `$CB000-$D7FFF` (declared with `; ram:`; zero at start, tables built lazily behind a magic long / the colour-table pointer WPTR; moved down by exactly `$10000` from `$D0000`/`$DB000` for the TOS 2.06 1 MB layout: same sizes, contents and generation).
  The tables cost about 18 VBL once (geometry product table 0.9 M cycles, window tables 2.0 M cycles). `rd_init` (site `$78f6`, the `jsr $fde0.l` of the race setup, after the game has built `$4564 $4644 $4ff8` and set `$135a`) calls both pre-warm entries so the generation happens while the race is set up, before the race loop (`$7a88`);
  the lazy paths stay as the fallback. `rd_init` requires `rd_geom rd_draw`; `rd_geom` and `rd_draw` are independent of each other. The 4 MB layout needs `pp_bigram_cache` (the tool refuses a HD build with `rd_*` without it).
- `mt_clock`, `mt_pre`, and a pacer = `mg_sync` + `mg_pace` (`default: yes`, below) or the options `mx_sync` + `mx_pre`, `mf_sync` + `mf_pre`, `mt_sync` (all `default: no`) (`work/notes/tick.md`, `work/notes/timing.md`, `work/notes/extrap.md`, `work/notes/mxfast.md`, `work/notes/integration.md` sections 8 and 12): the fixed real-time tick. `mt_clock` (VBL clock in 1/300 s, site `$d128`) is required by every pacer and `mt_pre` (latch guard before the first back-buffer write, site `$7b0a`); every pacer also requires `mt_pre`.
  `TICK equ 30` in `mt_sync.s`, `mg_sync.s`, `mx_sync.s` and `mf_sync.s` (5 VBL at 50 Hz, 6 at 60 Hz = 10 passes/s; exact at both): the game runs 20 % faster than the stock 8 MHz driving speed (8.33 passes/s) by design (user-approved) and at that speed on every CPU clock; a pass that needs more than a tick just runs late (no sleep, resync after more than 2 ticks). Change all four equates together.
- `mg_sync` (+ `mg_pace`; **`default: yes`**, user-approved with the final integration; replaces `mx_sync` + `mx_pre`): the extra in-between frames. Site `$7b52` (`tst.b $1024.w / bne.b $7b5e`, right after the HUD stage, before the collision/debris stages `$18888 $18c86 $18f0e`): with `$1024` = 0 the blob flips the main frame, draws the extra frames of the tick (scheduler: TICK 30, an extra starts only when `start + DEXT + SAFE + SAFEX <= NEXT`; each extra: ring/static/scroll advance, road geometry and draw, objects, HUD strip, flip), restores everything they changed (static ranges, ring windows (V bytes), the object slots that were active, 100 sprite-kernel longs + `$dafe`) and returns to `$7b58`; `mg_pace` (site `$7b74`) sleeps until the tick and flips only when the blob did not. No `mx_pre`: the slot state of the draw is read directly. Blobs `$B8100 $B8180 $B8380 $B8400`, data `$B8F04+4 $B8F20+224 $B9000+3584 $B9E00+256`. Only where the machine has spare time; measured with the final default set (steered driving, tick on, Hatari, `integration.md` section 12): **8 MHz STE one extra picture in 63 % of the racing ticks = 16.0 pictures/s (previous default `mx_sync` set: 29 % / 12.7), 16 MHz 2.0 extras per tick = 28.8 pictures/s, 32 MHz 4.0 = 47.9**; none while the car stands or the race is being set up. Game speed (10 passes/s), game state and the main frames are unchanged. **Deviations of the extras (user-approved): an extra frame shows the HUD strip of its main frame (the previous extras showed it one step ahead, e.g. the gauge after a crash slowdown), and in a collision bounce the extras of that pass show the car and road at the pre-bounce lateral position.** Margin: `SAFE equ 0` (clock units, negative = looser) plus the run-time word `SAFEX` (`$B8F6C`): margin 0 gives the most extras and the most uneven frame spacing (8.5 % of the 8 MHz ticks end more than 5 VBL late); `msrpatch.py build --set SAFE=3` (`tools/play.sh --safex 3`) 56 % extras / 15.3 pictures/s / 1.5 % late. `mg_sync` requires `mt_clock mt_pre mg_pace hd_stage`, conflicts `mt_sync mx_sync mx_pre mf_sync mf_pre`; `mg_pace` requires `mt_clock mt_pre mg_sync`, conflicts `mt_sync mx_sync mf_sync`.
- `mx_sync` (+ `mx_pre`, site `$7b46`; `default: no` since the final integration, the previous default pacer): the same kind of extra frames drawn AFTER the post stages (site `$7b74`) from a pre-draw copy of all object slots (`mx_pre`); 8 MHz STE one extra picture in 36 % of the racing ticks (13.4 pictures/s in the same final set), 16 MHz about 1.8 extras per tick, 32 MHz 3.9 (earlier set). `mx_sync` requires `mt_clock mt_pre mx_pre hd_stage` and conflicts `mt_sync mg_sync mg_pace mf_sync mf_pre`; `mx_pre` requires `mx_sync`. `mf_sync` + `mf_pre` (`default: no`) are bit-exact pictures of `mx_sync` with cheaper machinery (`mxfast.md`). `mt_sync` (`default: no`) is the fixed-tick-only pacer without extras: `tools/play.sh --noextrap` builds it for comparison.
- `test_blob36k` (`default: no`): payload-capacity test at the same site as `test_marker`: a blob at `$B3000` (beyond the image's natural end)
  plus 1 byte of `free` data at `$C16FF` pads the image to exactly `IMG_MAX_LEN` (61,440 B), and the blob writes `MSTM` + a 16-word ramp at
  `$B3010`. A pass proves the bigger RUNME data segment loads on 1 MB and the copy routine covers the whole image.
- `test_framecount` (`default: no`): per-frame counter at `$B2FF4` (site `$d1ca`, the flip), for A/B work through `live` and for comparing
  against `msrbench.py`'s flip count. `tools/msr_live_test.py` runs it on a snapshot.
- `test_marker` (`default: no`): hooks the game's first run-time code (`$6f5e`, `lea.l $70000.l,a0` in the trap #2 handler `$6f5a`) with a blob at `$B2800` that
  writes the long `MSTM` to `$B2FF0`, replays the `lea` and returns to `$6f64`. It proves staging, trampoline, patch application and the blob area.
  Check in the emulator: `m $b2700 8` -> `MSPO`, `m $b2ff0 4` -> `MSTM`.
- `mr_credit` (`default: yes`, `phase: stage1`, site `$78524`): the release credit `v@VERSION@ enhanced by dad_prg` (`patches/VERSION` is the one place of the version number:
  `msrpatch.py version [--credit]`, the `@VERSION@` token in sources and docs, zip names) at the bottom of the "Moonshine Racers" / hotrod title picture, in the game's own
  message font; blob `$BFD00`. Details, screenshots and gates: `work/notes/credit.md`.

## Floppy (original STX disks, `build --floppy`)
`python3 tools/msrpatch.py build --floppy [--only N ...] [--out build/floppy] [--zip]` builds the two-disk release from the original STX disks
(`originals/floppy/*.stx`, git-ignored; never modified): `build/floppy/disk_a.st` (disk A + payload + hooks + protection neutraliser) and `disk_b.st`
(byte-identical to the original disk B). Design, evidence and gates: `work/notes/floppy.md`; summary in `work/notes/delivery.md` section 7.
- **Payload delivery**: the boot sector's first original instruction (offset `$18`) branches to a stage-0 loader in the sector's free area; it reads the image
  (`core_floppy.s` trampoline at `$B2708`, site table at `$B2820`, blobs, 26,636 B with the default set) from blank sectors of disk A (track 0 sectors 2-10 and
  tracks 50-61 side 0; 129 sectors allocated, each checked blank) to `$B2700` with XBIOS `Floprd`, then the original boot code runs. The header (`60 04`,
  "MOON") is unchanged: the game recognises disk 1 by it. The same RAM patches (`patches/*.s` with a `; site:`) apply as in the HD build (`build --floppy`
  additionally requires their original bytes in the floppy game's RAM, `work/floppy/ram_answered.bin`: all current sites match). `$B2700` marker as in HD.
- `fl_hook` (`; media: floppy`, always included): disk A `$C350` (RAM `$6f50`) `move.l #$6f5a,$88.w / trap #2` -> `jmp $B2708.l`: the trampoline runs when the loader starts the game.
- `fl_deprot` (`; media: floppy`, default yes): disk A `$E3D0` (RAM `$7bd0`, the manual-lookup routine's first two instructions `7e02 3f07`) -> `bra.w $7d1a` (`6000 0148`),
  the routine's own "accepted" exit: the question is never asked. Instruction-level evidence: `floppy.md` section 6.
- `fl_driveb` (`; media: floppy`, default yes; `work/notes/floppy_driveb.md`): RAM site `$d6fa` (the game's only entry into its own FDC driver, which always asked for unit 0 = drive A) -> blob `$BB400-$BB52F`: disk 2 may be in
  drive B. The disk checks (boot sector of the disk in the drive: `MOON` at offset 2 = disk 1, `$66055505` at `$e` = disk 2) try the preferred drive (A at power-on) and then the other one; the drive that held the wanted disk is used for all reads
  until the next check. Drive B is only touched after a short own probe (restore with TR00 and no seek error, then an index pulse: a drive with a disk), so a machine WITHOUT drive B (or an empty one) is not left in the driver's 4.4 s FDC waits (13 s per check in Hatari).
  **One-drive users:** the swap route (disk 2 into A at the prompt) is unchanged; each key press at the prompt BEFORE the swap (disk 1 still in A = failed check) takes about 0.9 s longer (2.0 s if a drive B exists but is empty; Hatari 2.6.1, real FDC timing; real hardware not measured).
  Switch off: `python3 tools/msrpatch.py build --floppy --only <the default set minus fl_driveb>` (the list `tools/play.sh` builds: `msrpatch.py list | awk '$2 ~ /^yes/ && $1 !~ /^pp_/ && $1 != "fl_driveb" {print $1}'`); a `--no-driveb) DROP+=(fl_driveb) ;;` line in play.sh does it there.
- Disk 2 (one drive): the game asks for it itself ("Insert Disk 2 and press a key."); swap the disk in drive A and press a key. Hatari: `hatari-option --disk-a <copy of disk_b.st>` (floppy.md section 7). Two drives: disk 2 in drive B (`fl_driveb`; Hatari `--disk-b`, or `hatari-option --disk-b` at the prompt).
- The HD-only `pp_bigram_cache` (HAGA) and RUNME edits are not part of the floppy build.

## Tool
```
python3 tools/msrpatch.py list
python3 tools/msrpatch.py verify                      # every site's orig vs both RAM dumps, RUNME edit points, bss scan, HAGA edits: must end `ALL OK`
python3 tools/msrpatch.py build [--only N ...] [--set NAME=VALUE ...] [--out build/hd] [--zip [PATH]]    # --only replaces the default set (`--only` alone = zero patches); --set overrides a patch's `NAME equ` line (e.g. `--set SAFE=3`, mg's frame margin)
python3 tools/msrpatch.py build --floppy [--only N ...] [--set NAME=VALUE ...] [--out build/floppy] [--zip [PATH]]   # the floppy release (see Floppy)
python3 tools/msrpatch.py live  [--only N ...] [--out build/live/patches]         # <out>.img (load at $B2700) + <out>.json for stharness capture_frames(live=...)
python3 tools/msrpatch.py version [--credit]
python3 tools/msrpatch.py doc FILE                    # FILE with @VERSION@ and {PATCHES} replaced
```
Boot-test a build: `python3 tools/msr_boot_test.py --machine ste --mem 4096 --game build/marker --peek b2700 b2ff0` (cold boot, SPACE navigation to the first race,
raw memory printed). Instruments: `tools/msrhook.py` (registers/memory/RAM dump at given PCs during a cold boot).
