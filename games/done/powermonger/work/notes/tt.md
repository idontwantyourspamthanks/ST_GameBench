# Powermonger on the TT (user report, `dist/run_tt.sh`): invisible pointer, odd intro (PMTT, 2026-11-10)

Tags: **[obs]** raw tool output (logs and screenshots in `work/shots/tt/`, harness `tools/pmtt.py`); **[INFERENCE]** not run.
Setup reproduced headless with run_tt.sh's exact options (`--machine tt --tos TOS_3_06_uk.img --memsize 4096 --cpuclock 32 --monitor vga --gemdos-drive skip --acsi 0=<copy of the dist image> `, sound on with `SDL_AUDIODRIVER=dummy`, no `--fast-boot`): `pmtt.TT().to_map()` = wait for the PMBOOT line (it is up for ~3 s, VBL ~450..650), P, intro (space skips), name, options, chart, island, map view. The earlier TT cells of regression.md used the floppy build or `pm.PM` (`--harddrive` folder, `--monitor rgb`, `--fast-boot`, `--sound off`); the differences that matter here are none of those: both defects are in the game's code and show on the floppy build too (the floppy build was only used for the ST / Mega STE timing gates below).

## 1. Intro: two causes, both in the original code (not a phantom key)
* **CPU-speed timing** [obs]. Stage 1's picture sequence (`$660..`, 214 calls) is timed by three busy loops (`move.l #n,d0 / move.l #m,d1 / subi.l #1,d1 / bne.w`): `$1428` (15 x $500, 64 calls), `$144a` (15 x $800, 145 calls), `$146c` ($4ff x $500, 3 calls: the long holds). Entry-to-exit on the original floppy, 8 MHz, 50 Hz, Hatari `pc = $1428 && ($1428).w = $203c` and the routine's rts (`work/shots/tt/st3.log`): **$1428 = 4.94 VBL (60x5, 4x4), $144a = 7.92 VBL (134x8, 11x7), $146c = 420.3 VBL (8.4 s)**; ST 1.04 and STE 1.62 give identical entry-to-entry periods (5 / 8). A 68030 at 32 MHz without caches runs them ~10x faster, a Mega STE 16 MHz 2x.
* **Palette stores run past the palette** [obs]. Nine stores in stage 1 are `movem.l d0-d4,$ffff8250` (5 longs = 20 bytes; `$6e4 $71e $a70 $d32 $d6c $da6 $f9a $12a2 $12de`): the fifth long goes to `$ff8260/62`. On an ST/STE `$ff8260` gets 0 and `$ff8262` does not exist. On the TT `$ff8262` is the shifter mode and the long is the next table's first word (e.g. `$0776`): its high byte, the red nibble of a colour, is the TT resolution (Hatari video.c `Video_TTShiftMode_WriteWord`: `TTRes = byte($ff8262) & 7`): 7 = TT high (mono), 4 = TT low. At the first hold (`pc = $cd788`, `r`/`m` dump) `$ff8240..` read all zero and `$ff8260` = `00 00 00 76`: the screen is black. The text and castle pictures were never visible on the TT, even when the delays were right (a run with only the delay patch: black for 8.4 s, then the hall).
* Not the cause: key/mouse. The skip test is the stage-1 VBL handler `$2c78`: `cmpi.b #$39,$fffc02` (last ACIA byte = space make code) -> `$12e8` (go on to the game); [obs] `--trace ikbd_all`: after P the only ACIA byte is the P break code `$99`, the handler sees `$99` every VBL. Mouse motion during the intro does not skip anything [obs]. Without a key the intro ends in the credits loop (`$12aa`, waits for space) forever on every machine.
* Unpatched original on a TT: not run; the original does not start there at all without cacroff (loading.md section 9), so the comparison is "patched, intro patches off" (= the user's image): black until the hall, no text, no castle.

## 2. Pointer: the shifter base is followed LIVE by Hatari's TT [obs, with proof by the fix]
* The pointer position is right ($2df92/94, $1c492/94 follow the mouse), the pointer rows are written every VBL by the VBL handler (`$1390` block) into `[$2df78]`, but on the TT it is **invisible in the front end** (name, option, chart screens) and **absent in 12 of 40 frames in the map view** (`work/shots/tt/crop_cmp.png`, the user's image: 28/40 frames show the arrow). Same with p4_ptr_a/b removed and with no p4_ patch at all (`MIN` build: core + hd_* only): not ours.
* Mechanism. The game's flip `$187a` swaps `[$2df78]/[$2df7c]` and writes the new base to `$ff8201/03` (`move.l d0,$8200.w`); the VBL handler draws the pointer into `[$2df78]`, the buffer that is displayed *in that frame* on an ST/STE (the base is latched at the start of the next frame; p4_chase's notes use the same fact). The menu loop (`$13e1e`: wait VBL `$1870`, draw, `$187a`) flips right after every VBL handler [obs: at every `pc = $1282` hit `[$2df78]` = the hardware base and it alternates `$1c700`/`$24400`]. Hatari's TT video (`Video_TT_RasterHBL`: `pVideoRaster = Video_GetScreenBaseAddr() + ...` from the live register) switches to the new buffer at once, which has no pointer yet: the pointer is always drawn into the buffer that has just been put away. In the map view (flips 1 in 3 frames) it is missing for the frames after a flip. [INFERENCE] a real TT latches the base at the vertical sync like an ST, so it would be fine there; the patch is harmless either way.
* No IKBD problem on the TT: [obs] `$bdc04 = $b17e0002` (p4_spr's probe finds no blitter on the TT: no HOG blits, so PMBusErr's overrun does not apply), 40 random mouse moves in the map view: $2df92/94 always in range. The user's image predates the p6_cpy / p4_clamp fix (image 12:16, fix 13:41); the new image has both.

## 3. Patches (all `; default: yes`, applied on every machine unless noted)
| patch | site | what |
|---|---|---|
| `pm_intro_a/b/c` | stage 1 `$1428 $144a $146c` (6 B each) | `jmp` to waits in real time: 30 / 48 / 2522 units of 1/300 s (= 100 ms, 160 ms, 8.41 s) by counting the intro's own VBL flag `$2ca0` (`clr.w`, then poll for 1) and subtracting 6 (50 Hz) or 5 (60 Hz, read from `$ff820a` bit 1, as `tick_head`) per VBL; the overshoot is carried (`CARRY`), so the long-run rate is exact at 60 Hz. Blob `$cd780` (68 B, `pm_` range). d0/d1 only. The skip key works as before (the VBL handler does it). |
| `pm_intro_pal` | stage 1 `$660` (6 B) | the one site; runs the displaced `move.l d0,$2ca2.l`, then changes the register mask of the nine stores from `$001f` to `$000f` (4 longs = `$ff8250..$ff825f`) after checking each is `$001f`, `jmp $666`. Blob `$cd800`. On ST/STE only `$ff8260` is no longer written (with the value it holds, 0). |
| `tt_ptr` | stage 2 `$1898` (8 B: the flip's `move.w #0,$2df8c`) | `init` (INITTBL, supervisor, cookie jar intact) sets `LIVE` (`$baaf0`) from the `_MCH` high word 2 (TT only; Falcon not tested). The hook runs the displaced instruction, and if `LIVE` and the pointer is not hidden (`$1c6b2`), runs a verbatim copy of the VBL handler's pointer block (original bytes `$1390..$14c3`, relative branches; restore at `[$1c49a]`, save + draw at `[$2df92/94]` into the NEW `[$2df78]`) with SR IPL 4 (VBL/HBL cannot interleave, the handler's own context). Cost on a TT 0.4 ms per flip; on ST/STE one `tst.b`/`beq`. New prefix `tt_` in `pmpatch.PREFIX_RANGES`: `$BA900..$BAFFF` (outside the HD overlay window). |

## 4. Gates [obs unless marked]
* **Intro durations, patched, entry to exit of the waits** (`work/shots/tt/{ste6,st7,tt6,mste7}.log`, VBL counts): STE 1.62 50 Hz HD image: 5.0 / 8.0 / 420.3 (original 4.94 / 7.92 / 420.3); ST 1.04 50 Hz floppy build: 5.0 / 8.0 / 420.3; **Mega STE 2.06 4 MB 16 MHz 60 Hz: 6.0 / 9.6 / 504.7; TT 32 MHz 60 Hz: 6.0 / 9.6 / 504.7** (= 100 ms / 160 ms / 8.41 s). Within 0.1 VBL of the original at 50 Hz, the same real time at 60 Hz. The fade/animation steps are the 64 + 145 short calls, so they step at the original pace.
* **Intro pictures**: TT patched: black, text "After a long journey...", castle, hall in order (`work/shots/tt/t_sheet.png`; the user's image: only the hall). STE original vs patched, 90 screenshots each: the static hold frames are bit-identical (6 of the top 6 frame hashes in both runs), so `pm_intro_pal` changes no ST pixel.
* **Skip**: `pmtt.to_map()` (space every 4 s) reaches the name prompt on the TT and the STE with the patches (name at 25 s on the TT).
* **Pointer**: TT, patched: front end shows the arrow and follows the mouse (`min_opt.png` shows none without the patch, `v5_opt.png` with it); map view 30/30 and 40/40 frames with the arrow (user's image 28/40); chart screen too. STE patched: `LIVE` = 0, `PMPO`, `FLAGS` 3, arrow visible, map view reached.
* **Full cold path on the final image** (copy of the new dist image, run_tt options): `PMPO`, `FLAGS` 3, `LIVE` = $ff, map view, pointer in 30/30 frames.
* **Not run**: `pmab` for `tt_ptr` (its live harness is STE and bypasses `init`, so `LIVE` would be uninitialised; on ST/STE the hook is a `tst.b`/`beq.s` after the displaced instruction, pixel-neutral by construction [INFERENCE]); Falcon (the pointer may need the same hook; not tested); real hardware; TT with the original floppy; ST with the HD image.
* The Mega STE HD-image run (ACSI) hung Hatari after repeated keypresses at the PMBOOT prompt (harness issue, not investigated); the Mega STE timing above is from the floppy build.

## 6. Update 2026-11-10 (PMIntegrate, combined default set; `combined.md`)
* **`tt_ptr` moved from `$1898` to `$188c`.** p7_triple_tail (now default) owns the flip's last instruction `move.w #0,$2df8c.l` at `$1898`; the build refused both (`site overlap`). The hook now replaces `move.l d0,$2df78.l` (`$188c`, 6 B, `jsr tt_flip`; the first instruction of `tt_flip` is that displaced move, then the pointer block, all registers saved), so the pointer is drawn into the new displayed buffer BEFORE the flip writes `$ff8201/03` (the section 3 table row describes the old place). With three buffers: the pointer record `[$1c49a]` lies inside the buffer about to be scanned at 134 of 134 flip returns on the TT.
* **Falcon too.** The first Falcon cell of the combined set showed the pointer in 17 of 20 screenshots, and the previous default set 16 of 20 (Hatari's Falcon video follows the base register live like the TT). `init` now also sets `LIVE` for `_MCH` high word 3: 20 of 20 and 66 of 66 flip returns (final build 67 of 67).
