# v1.2.1 hardening: the YM I/O port direction (PSG reg 7)

Audit row: `tools/hatari-strict/AUDIT_2026-11-20.md` (Hunter). Gate: strict Hatari (`tools/hatari-strict/`) + `tools/psgcheck.py`, driven by `tools/hunt_psg.py` (cells) and `tools/hunt_psg_all.sh before|after` (logs in `work/psg/`, git-ignored).

## The change
`patches/snd_core.s` `snd_ymsilence` (called once per 3D session by `snd_enter`) read PSG reg 7 back and ORed `$3f`. Now: select 7, write `$ff` (absolute), then reg 8/9/10 := 0, all with SR raised to `$2700` and restored (select/data pairs atomic). Same code size (the blob end and the `sky2_` window are unchanged; `huntpatch.py verify` ALL OK).
- `$ff` = tone and noise off on A/B/C and BOTH I/O ports outputs (bit 6 = port A: floppy drive select/side; bit 7 = port B). It is what the original driver leaves after its init (`$ff@11ab0`, `$f8@119ca` per effect).
- In the 3D view the driver's 16 YM operands are redirected to the scratch (`snd_ympatch`), so its own reg-7 writes (`$f8`/`$ff` per effect) never reach the chip; `snd_ymsilence` is the only reg-7 write of any Hunter patch (no other patch touches `$ff8800`; `grep` over `patches/*.s`). The YM does not play in the 3D view on STE-class machines (DMA samples), so there is no tone/noise state to preserve. Nothing the patch skips restored reg 7 in 3D.
- ST (and the paths where `snd_core` is inactive) never run the routine.
- Version 1.2 -> **1.2.1** (`patches/hn_credit.s` `; version:`): title line `v1.2.1 enhanced by dad_prg` (26 chars, x = 95..224, inside the black strip; all glyphs `v 1 2 . enhancedby_dprg` exist in the 4x6 font; `huntcredit.py` RECT updated). Release note in PATCHES.TXT / FLOPPY.TXT / FLOPPY2.TXT: "hardening: the YM I/O port direction is now set explicitly (no known failure)".

A/B reading: on STE/Mega STE the reg-7 value history is `$c0 (TOS) -> $fe (TOS bell) -> $f8 (title tune) -> $ff (title tune end) -> $ff@8e1fx (snd_ymsilence)` in both; the only change is the pc of the last write (`8e1fa` before, `8e1f6` after: the value is now a constant `$ff`, not read-back). On ST (patch inactive) the sequences are identical before/after (`$c0 $fe $f8 $ff` then the original game's own `$df/$ef/$f7` writes (pc 112ca)). Evidence that the floppy works AFTER the patch took the YM (strict model, port A must be an output): `work/psg/k_floppy_ste.kept` (v1.2.1 floppy, STE): 3 snd_ymsilence writes (one per 3D session: entry, after Save, after Load), 598 FDC commands after the first one, psgcheck PASS, final reg 7 = `$ff`. Negative control (strict build catches a clear bit 6) is the Midwinter 2 v1.6 case in `tools/hatari-strict/README.md`; not repeated for Hunter.

## NON-ATOMIC verdicts (pre-existing game code, not ours)
`before_hd_mste16` and `after_floppy_mste8` (and two earlier runs of the same shipped v1.2: floppy STE, floppy Mega STE 8 MHz) show: `NON-ATOMIC select/write: select reg 7 at pc=11a9e ... overwritten by another code's select of reg 10 before the data write at pc=11ab0`. Pinned from a RAM dump of the UNPATCHED original at the title (Hatari STE): `sub_11a9e` is the original title-tune shutdown, a read-modify-write of reg 7 (`move.b #7,$ff8800 / move.b #7,d0 / or.b $ff8802,d0 / move.b d0,$ff8802`) with SR still `$2300` (it only sets `$2700` at `11ab6`). The interrupting writer is the ORIGINAL title digi player on MFP Timer A (vector `$134` = `$11ae0`, IERA `$20` at the title): it selects reg 8 and reg 10 (`move.b #$a,$8800.w` at `$11b04`) and writes the sample nibbles. Both are original game code outside every Hunter patch. Effect: the OR value lands in reg 10 instead of reg 7 (one volume blip at the end of the title tune); reg 7 keeps its old bits 6/7, so no port-direction hazard. It is a race: observed in about 4 of 35 patched/shipped full-navigation cells (v1.2 and v1.2.1 alike), 0 of 13 unpatched-original runs (title-only and full navigation); the code is identical byte for byte and the Timer A path is untouched, so [INFERENCE] it occurs on the unpatched game too. The PSG gate for Hunter therefore treats this one pc pair (`11a9e`/`11ab0`) as a known original-game finding.

Observed in about 4 of 35 patched/shipped full-navigation strict cells and 0 of 13 unpatched-original runs. Both routines are byte-identical original code and no Hunter patch touches Timer A or the title, so [INFERENCE] the race exists unpatched too; our patches may change the timing enough to widen or narrow the window (unmeasured). No failure mode: the effect is one reg-10 volume value, and reg 7's port bits are untouched.
