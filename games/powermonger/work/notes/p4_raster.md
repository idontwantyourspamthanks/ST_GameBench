## 1. The gate `tools/pmab.py` (docstring has the full contract)
Hunter's trick (compare the first patched frame / N flips later) fails here because the world runs on the VBL counter: a faster pass moves the same world state to another pass. Instead BOTH runs carry the tick_* set and frames are matched by (world tick `$4bb3e`, pass kind R/T) which fixes the world state (a T pass renders before the men/weather of its tick run; an R pass renders after). At each flip entry both screen buffers go through a FIFO (3 persistent breakpoints only; one breakpoint per flip made Hatari 50x slower), so: `back` (new render, byte-for-byte), `shown` (previous frame + software pointer, compared when previous key and pointer position agree), cycles S1(`$13096`)->S2(`$187a`), fps over the window.
Findings that shaped it (all observed):
* The game polls the IKBD every VBL (`$0D`), the reply handler copies the position to `$2df92/94` (`$194c/$1956`): pokes are overwritten within a VBL. `test_walk*` replaces both copies by PX/PY set at the tick increment (`$13034`) from a 16-position table (edges, x=304 two-column wrap, x>304 one column, y>184 clip, corners).
* A first version changed the position at flips: frames then differed at row 30 (army status icon blit into the background picture `$78000`, drawn by logic via `$16808->$12326`) because the UI logic reads `$2df92` and the S/R pass mix differs between runs. Position must be a function of the tick for the whole tick.
* Self test (no patch): +-0.00..0.08 % cycles, IDENTICAL. Negative control `--neg` (pointer moves in one run only): DIFFER (SHOWN and BACK).
* Hatari: `e` prints `#N/-M (dec)` for values >= 2^31 (regex fix); never `pkill hatari`; the cpuclock switch to 16 MHz lands at a wall-clock-dependent instant, so at 16 MHz flip 1 may differ by one tick (NOTE only; frames are matched by key).
* Also printed for the base run: frames equal to the frame two flips earlier and consecutive same-tick R frames (item 6).

## 3. Item 2, pointer: `p4_ptr_a` (`$1390`) + `p4_ptr_b` (`$14c4`)
Skip restore+draw when provably the same: `[$1c49a]` equals the address recorded after the last draw, `[$2df78]/[$2df92]/[$2df94]` equal that draw's inputs, `[$2c1be] == 0` (no animation step), and the 16 x (16|8) byte rectangle under the pointer equals the image the draw left (cmpm). Then restore writes S over it and the draw saves S again and ORs the pointer back: same bytes, same save area. A flip changes `[$2df78]`, so the first VBL after a flip is the full path. Part B records the draw (inputs re-checked: mouse words changed during the draw => no entry). Other writers into the displayed buffer exist (`$3f14` icon blits in `$3e06`, observed row 30 changes), which is why the rectangle is compared rather than trusted. Each hook alone is harmless. Gate: `--walk`, IDENTICAL on all three snapshots and both clocks (table 0). At 16 MHz the saving (-1.9..-2.2 %) is below one VBL per pass, so fps barely moves.

## 4. Item 3, the 3D window copy `$12ce0`
* What it is: `jsr $12ce0` at `$13096` copies 32000 B from `[$e0d4]` = `$78000` (QAZ.DAT frame picture: decoration, HUD panels, the pit the terrain is painted on; modified at run time by status icons) to the back buffer `[$2df7c]` at the start of every rendered pass; also `$13cc6/$13cd8` (both buffers at view start) and `$188d4`. It cannot be removed by flipping: the renderer only draws over the picture (terrain covers part of the window, sprites/HUD/text are masked or partial), so every pass needs the clean picture.
* Window-only copy: union over 26-44 frames of bytes where the finished back buffer differs from `$78000`: get_men 6673 B (5879 inside the window box cols 5-19 x rows 13-165, 794 outside), map_idle 8092 (7870 / 222), battle_320 7959 (6836 / 1123). The window box is 61 % of the screen, so <= ~64 k cycles (3 %) could be saved, but the outside bytes (left panel, top bar, bottom icon bar, dialogs/tooltips drawn by `$6a3a/$7a56/$d23a/$7202`) rely on the restore, and no complete list of writers was proven: NOT built (exactness).
* Cost of the copy itself (`test_copy`, interrupts masked, 32000 B): original 8-reg movem pairs 162 236 cycles, 12-reg movem loop 154 708 (-4.6 %), blitter HOG 128 060 (-21 %), blitter shared + CPU polling 285 264 (2.2x slower than HOG), shared with a 2000-iteration CPU loop meanwhile 290 416 (the loop is hidden but the total is far worse). Same cycle counts at 16 MHz in Hatari. HOG blocks interrupts for the whole blit (the sample IRQ, VBL): a 32000 B blit would hold the bus ~128 k cycles; split into chunks the setup eats the gain. Not built.
* `p4_chase` (site `$13090`, replaces `jsr $1870; jsr $12ce0`): the old displayed buffer stays on screen until the VBL, the idle wait is wasted, and rows above the video counter (`$ff8205/07/09`, minus 3 rows) are already displayed, so they can be copied behind the beam; after the flag the rest is copied and the pointer restore rectangle (saved before the VBL) is copied again. Result: fps +2.0 % (get_men 8 MHz) .. +8.0 % (battle_320 16 MHz); the gain is limited by the slack left after the T-pass logic (E[min(copy, slack)] ~ 34 k cycles at 8 MHz). **Defect found by the gate: with the pointer at x = 304, y >= 184 (two columns, last row, spills 8 B into the next buffer's row 0) shown frames differ in 8 bytes at row 0 (`SHOWN DIFFER (pointer 304,184)` in the combined + chase runs, 8 and 16 MHz). My fix (copy row 0's 8 bytes again) did not remove it (re-run still DIFFER); not understood, out of budget.** Also needs real-hardware verification of the beam logic. Recommendation: do not ship. Without chase every combined row is IDENTICAL.

## 5. Item 4, sprite blits `$12326` / `$124a8` -> `p4_spr`
`$124a8` is the 3-column variant (96 % of the sprite cycles; default zoom calls it ~20x per pass for 24-row sprites at 480 B, `$37c7c`; zoom <= 3 uses 32 rows `$3af1c`; zoom > 5 the 16 px variant `$122b6`, untouched). Contract: a0 screen (y*160 + x/16*8 added), a1 rows (20 B: M0 P0..P3 | M1 Q0..Q3), d0 = s = x&15, d2 = rows; ~770 cycles/row (10 `ror.l` + the middle column read-modify-written twice). Exact algebra: ((D&Ma|Pa)&Mb|Pb) = D&(Ma&Mb) | (Pa&Mb)|Pb, i.e. one `D&M'|P'` per column with M'/P' the shifted words (ones fill for masks, zero fill for planes). Registers left as the original (a0 += 160 rows, a1 += 20 rows, d0, d1 = $88, d2.w = $ffff, a2-a6 kept).
* **A. Blitter (HOG)**, 8 passes (per plane: AND the mask, OR the plane): skew s, **NFSR is SKEW bit 6** (bit 7 = FXSR; my first guess was reversed and gave garbage), xcount 3, source xinc 10 / yinc 10, dest xinc 8 / yinc 144, endmask1 `$ffff>>s`, endmask3 `$ffff<<(16-s)` **in both passes** (bits outside the sprite come from the shifter's previous word, e.g. the OR pass wrote stray bits until the masks were also used there). Used only if FLAGS bit0 and a bus-error-safe lazy probe of `$ff8a28/$ff8a2a` (TT/Falcon answer FLAGS bit0 but have no blitter). HOG pass <= ~900 cycles of interrupt latency: sound via the YM sample IRQ gets that much jitter per sprite pass (DMA sound unaffected). Shared mode not used: the next terrain fill writes the same buffer, so every sprite must be finished before the CPU continues (measured shared mode 2.2x slower anyway).
* **B. Pre-shifted cache** (every machine): per (a1, s) a 36 B/row entry (3 mask longs + 6 plane longs), draw = movem + 5 and.l + 5 or.l + movem + 1 long, ~325 cycles/row. 8 sets x 6 ways x 1280 B (<= 32 rows) = 61440 B at `$be000`, tags `$bdc10`, lazy init guarded by a magic word (HD stage 1 bounces SPRITE40.DAT through the p4_ range, so no zero-at-boot assumption; the blitter mode word has a magic high word too). Only a1 in the sprite sheets `$312a0..$3f29c` (SPRITE16/24/32.DAT, loaded to fixed addresses, written by no game code [INFERENCE: static; three RAM dumps agree]); s = 0, rows > 32 and other addresses run the original. Hit rate [obs, `$124a8` trace over 700 VBL]: get_men 977 calls / 17 distinct (a1,s,rows); map_idle 549 / 17; battle_320 928 / 17; LRU of 40 entries = 97-98 % hits.
* Exactness proof: `test_blit` random differential test inside the running game (random shift 0..15, rows 1..32, column 0..17, random sprite rows incl. bits a real sprite never has, real sheet data for the cache, random destination, 160 B rows compared, final a0/a1/d0/d1/d2 compared, miss and hit paths): **60 000 trials per mode, 0 mismatches, 0 register mismatches, both modes** (SYIN=20 control: 298 of 300 mismatch, so the test is sensitive). Run: apply `test_blit p4_spr` live, `w $ce504 <N>`, `w $ce574 $b1 $7e $00 <1|2>`, `w $ce56c $00 <0|1>` (1 = sheet data), `w $ce500 $00 $01`, read `m $ce510 36` (RES, `$600d` at +32).
* Blitter vs pre-shifted: blitter -12 % vs -10 % at 8 MHz; Hatari charges the blitter the same cycles at 16 MHz, a real Mega STE blitter runs at 8 MHz so the blitter advantage there is [INFERENCE] smaller or negative. Both identical in the gate. The lead can ship auto (blitter on STE, cache on ST) or force the cache (`BLT = $b17e0002`).

## 6. Item 5, maths tables: not built
Profile (`work/prof/*_8mhz.txt`, per whole profile): all mul/div = 2.98 % (get_men), of which the 7 triangle-setup `divu` (`$f010 $f01c $f046 $f052 $f0b4... $f0c0 $f0fe $f10a`) = 2.4 %, and the constant multiplies `#$37` (55) 0.05 %, `#$1e0` 0.04 %, pointer `#$a0` (now skipped), `#316`/`#$20`/`divu #20` < 0.01 % each: not measurable, and the 4-byte `mulu.w #imm,dn` cannot hold a 6-byte jsr without replacing the next instruction. Triangle divides: operands are |dx| 0..255 and dy 1..199 (vertex x < `$ff0000`, y <= 199): `(dx<<16)/dy` for dx < dy, `((dx<<8)/dy)<<8` for dy <= dx (the overflow clamp `$10000` cannot occur). Exact table = 39 KB + 62 KB, p4 has 69 KB and p4_spr uses 62; a reciprocal-multiply replacement needs two `mulu` (~90-120 cycles) = no gain over `divu` (avg 132). Not worth it.

## 7. Item 6, static-frame skip: measured, not built
Base-run counts (700-1200 VBL): frames equal to the frame two flips earlier: map_idle 8 MHz 16/28, everything else 0/49..0/191 (get_men 16 MHz 0/191, battle_320 16 MHz 2/113, map_idle 16 MHz 0/147); consecutive same-tick R frames: get_men 16 MHz 8/8 identical but only 8 pairs in 193 frames. An exact skip needs an input signature over everything the renderer, HUD and UI read (world state, camera, UI windows, pointer-dependent items, texture dissolve); skipping only the landscape leaves HUD overlays on a buffer that was not restored. The only profitable case (quiet map at 8 MHz) is the one where frame rate is irrelevant. Not built.
