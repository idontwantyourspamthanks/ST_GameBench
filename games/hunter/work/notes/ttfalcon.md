# Hunter on TT (TOS 3.06) and Falcon (TOS 4.04), Hatari 2.6.1 (HunterTTF)

Tags: **[obs]** observed, **[disasm]** read from disassembly, **[INFERENCE]** not verified.
Tool: `tools/hunt_ttf.py` (HD cold boot cell: `--machine tt|falcon --game DIR [--bus] [--poke-mch 0x20000]`), `tools/huntfloppy.py --machine tt|falcon --pb-at 35` (floppy cells; the TT/Falcon boot screens are white, so auto-detecting "Paper Bag presents" fires at once: use `--pb-at 35`). Builds used: `huntpatch.py build --out build/ttf_hd --samples build/hunter_snd.bin` and `build --floppy --out build/ttf_fl --samples ...` (default patch set p4_ikbd/p4_poly/p4_edge/snd_core).

| machine | build | result [obs] |
|---|---|---|
| TT 3.06, 4 MB, ACSI+HDDRIVER | HD, unpatched (PP original) | **does not run**: second HDDRIVER finds no drive, the game executes unloaded data, double bus error, Hatari halts ("CPU halted" dialog). With the cookie poke of section 2 it reaches the 3D view (`in_game` True, 25 fps = the game's 2-VBL cap at 32 MHz). |
| TT 3.06 | HD, patched (this work) | **3D view**, `MARKER=HNPO`, `FLAGS=3`, fps 25.00. No poke needed (START patch `mchfix`). |
| TT 3.06 | floppy, original Paper Bag | **does not run**: title and menus load, "Action" resets the machine (loader FDC time-out, section 4). With the time-out constant poked it passes "Action". |
| TT 3.06 | floppy, patched | **3D view**, `HNPO`, `FLAGS=3`, payload mode 2 (DMA sound), 6 s WAV rms 781 / peak 5101, fps 25.00. |
| Falcon 4.04, 4 MB | floppy, original | **does not run**: same reset after "Action". |
| Falcon 4.04 | floppy, patched | **3D view**, `HNPO`, `FLAGS=3`, payload mode 2, WAV rms 781 / peak 5101 (identical to TT), fps 16.60. |
| Falcon 4.04 | HD, unpatched and patched | **not testable here** (section 3). Not our code: the failure is HDDRIVER's drive scan, before START runs. |
Regression after the core/floppy changes [obs]: STE 1.62 1 MB HD (`HNPO`, fps 5.0) and STE floppy (`HNPO`, fps 4.80) still boot to the 3D view. ST/Mega STE were not re-run; the new code is 68000-safe by construction (illegal-instruction path) [INFERENCE for ST, observed only on the STE 68000].

## 2. TT HD: the game's cookie jar says "Falcon" (PP's, fixed in our START)
- Harness: the earlier "no screenshot" was the Hatari "Detected double bus/address error => CPU halted!" dialog, which blocks the fifo (`xwd`/`import` of the Xvfb root shows it). `hunter.py build_hd` also copied `build/` and `dist/` into the disk image (now skipped).
- `hunter.py --bus acsi` on a TT works: TOS 3.06 boots HDDRIVER (`Atari ACSI (ICD) 0.0 ... Drives: C`) and START shows its HW screen ("Machine: TT", START knows type 5; `--conout 2` prints console text into the Hatari log).
- START picks `D15R_F5.FIC` (the Falcon/TT loader) when `$6a0` is set (TT and Falcon both set it) [disasm START text $236/$242]. F5's cookie jar at `$d0edc` is `_CPU=$1e, _MCH=$00030000, _IDT` (H5's: `_CPU=0, _MCH=0`) [obs from the depacked file].
- START runs the root sector (HDDRIVER) a second time inside that world (text $590, `jsr (a0)`). HDDRIVER reads `_MCH`; on a "Falcon" it skips ACSI. Log [obs]: second run prints `Atari SCSI 7: [No LUN configured]` / `No partitions`; first run (real TOS jar) prints the ACSI drive. Then F5 reads FILES through the missing drive, the game jumps into unloaded `$1167a`.
- Proof: debugger breakpoint at START's `jsr (a0)`, `w $d0ee8 00 02 00 00` (`_MCH` = TT): 2nd HDDRIVER prints `Atari ACSI (ICD) 0.0 ... Drives: C`, game reaches MAIN OPTIONS and the 3D view (`hunt_ttf.py --poke-mch 0x20000`).
- Fix (ours): `patches/core.s` segment `mchfix` (58 bytes at START text $7fc0, same dead zone as the stub), START's `4e90 7e1c` at $590 becomes `bsr.w mchfix`. On START type 5 and the F5 jar tag `_MCH` it writes `$00020000` for the duration of the root-sector run only and restores the value. Machine type != 5 or other jar: plain `jsr (a0)`. A real TT with a SCSI disk is unaffected [INFERENCE]; a real TT with ACSI HDDRIVER now gets its drive.
- Boot with the build: `hunt_ttf.py tt_patched_nopoke --machine tt --game build/ttf_hd` -> `BOOT OK ... HNPO FLAGS=3 fps=25.00 (53 s)`; unpatched without poke: `BOOT FAILED ... alive=False`.
- TT SCSI (`--bus scsi`, with and without `--scsi-ver 2`): HDDRIVER 10.15 prints `Atari ACSI 0.0: [No device]`, no SCSI drive; Hatari's NCR5380 emulation is incomplete. Not usable. TT-RAM (`--ttram 8`) only slows the boot (memory test); not examined further.

## 3. Falcon HD: Hatari cannot give HDDRIVER a drive
- TOS 4.04 has no ACSI (Hatari manual says so too): `--acsi` boots nothing. `--ide-master` image: TOS 4.04 reads sector 0, HDDRIVER's boot code runs (banner appears, `--trace ide` shows IDENTIFY and reads of the partition/HDDRIVER.SYS), then HDDRIVER prints `Atari SCSI 7: [No LUN configured]` / `No partitions` and issues no IDE command at all (its probe reads `$fff00039` once, status `$50`; breakpoints at its IDE command entry `$126da` never hit) [obs]. `--ide-swap on` breaks the boot code; `off`/`auto` identical. Falcon SCSI (`--scsi`): boots, `No LUN configured`, no drive.
- TOS 4.04's native IDE driver does not map C: either (`_drvbits` stays `$0b`; with partition id `GEM` it still reads only sector 0, BGM and a DOS MBR also nothing). EmuTOS on the Falcon maps C: from the same image (`_drvbits $0f`), so the image and Hatari's IDE are fine [obs].
- GEMDOS-HD (`--harddrive`): START (TT, 40 s) loads PCH/D15R_F5/HUM through it and then `Pterm0` (no HD driver: START's driver check needs a real disk; TT trace `Pterm0() at PC 0x16ADA`). Falcon: reached `HUNTER.PCH` within 40 s, not followed further. Gamex does not tolerate GEMDOS-HD (same conclusion as boot.md on the STE).
- So the Falcon HD build (F5 loader, Falcon video/cache setup of START's M menu) is unverified here. What is verified on the Falcon is the resident game, our patches, probe and DMA sound via the floppy build. [INFERENCE] the HD build adds no Falcon-specific code of ours except `cflush`; `mchfix` does nothing on type 4.

## 4. Floppy on TT/Falcon: the loader's FDC time-out depends on CPU speed
- Original Paper Bag: after "Start new game / Action" the machine resets to "Paper Bag presents". Chain [obs]: game exception handler `$10f74` (clears memory, resets) entered with a format-2 frame, vector `$014` = divide by zero at loader `$d480` (`divs.w d1,d0`, d1 = sectors per track from the boot sector). Breakpoints on loader `$d474` show the sector-0 read returning all zeros and d4 = 0, and the wait routine's time-out exit (`$d52e st.b d3`) fires with d2 = 0.
- The wait is a loop count: `move.l #$70000,d2 / btst.b #5,$fa01.w / beq / subq.l #1,d2 / bne` at loader `$d51c` [disasm]: about 2.4 s on an 8 MHz 68000, about 0.2 s on a 030 with the instruction cache (my estimate from the cycle counts, [INFERENCE]), shorter than a long seek. Proof: in the unpatched floppy on TT, `w $d51e $01 $00 $00 $00` (constant `$1000000`) before "Action" -> the game gets past the load (reaches the name screen). Same reset on Falcon (16 MHz); TT at `--cpuclock 16` still fails. Hatari's data-cache switch is not the cause (`CACR=$3011` poke did not help; `--data-cache false` made the title load fail instead).
- Fix (ours, `patches/core_floppy.s` stage2): on 68020/030 the constant becomes `$700000`, on 68040/060 `$1c00000` (checked: opcode `243c` and old value `$70000` at `$d51c`, else untouched); 68000/68010 unchanged, so the ST/STE/Mega STE loader behaves exactly as before. Patched floppy then plays through on TT and Falcon (table above).
- The Paper Bag loader never flushes caches after its DMA reads. A 68030 does not snoop DMA, so a cached sector buffer could be stale on real hardware. Hatari did not show it with its default data cache. As a precaution stage1 switches the 68030 data cache off (CACR bit 8) from the moment the loader's own FDC code starts [INFERENCE: not provable in Hatari]. The cost was not measured; if the user wants it gone it is the `moveq #1,d2` in stage1.

## 5. Probe, caches, payload placement
- STE probe on TT and Falcon: `FLAGS=3` on both (DMA control `$ff8901` answers, frame-start mid byte reads back) [obs]. No bus error, bit2 clear. Plain ST still gives 6 (observed earlier).
- DMA sound: payload mode 2 on TT and Falcon, identical 6 s captures (rms 781, peak 5101; the same injected explosion as the STE test; STE reference in floppy.md was rms 885 on a different run) [obs]. Microwire write is bus-error guarded already; the Falcon has none. `snd_dmapos` uses `movep.l` (a 68060 without the support package would trap it) [INFERENCE: not testable].
- Instruction cache: START depacks the game, applies PP's patches and copies the `$150` hook with data writes; we then patch more. HDDRIVER's resident code on a TT/Falcon sits at `$11384`/`$12624`, inside the game's `$800..$12003`, so stale instruction-cache lines are plausible on real hardware [INFERENCE]; Hatari's TT/Falcon run in 030(CED) mode did not show it. Added: `cflush` at the end of `hnentry` (HD, and floppy through `jsr PAYLOAD+4`) and in floppy stage2: finds the CPU by executing under temporary `$10`/`$2c` handlers (`movec cacr,d0` illegal = 68000/010; `cpusha bc` line-F = 68020/030 -> CACR |= `$0808`; no fault = 68040/060 `cpusha bc` did the flush). `core.s` payload entry grew to 260 bytes, so the load-hook segment moved `$8bb00` -> `$8bb40` (site-table area untouched). Seen working on 68000 (STE) and 68030 (TT, Falcon: `HNPO`, game runs); the 040/060 branch was not executed anywhere [INFERENCE].
- Payload addresses: everything stays in ST-RAM (`$8BA00..$AEFFF`, bank `$90000`); START's HDDRIVER pool on 2 MB+ is `$186000` (class >= 4); a TT/Falcon with TT-RAM only adds memory above 16 MB that the game never touches. 4 MB ST-RAM was the only size run on TT/Falcon.
- START's Malloc emulation (`$7f0`): for `$6a0` machines START patches the function-number offset to 8(a7) (68020 frame) but not the argument offsets (`$8(a7)`, `$a(a7)`), so `Malloc(-1)` returns the pool base as "size" and Mshrink returns -40 on a 030. HDDRIVER's 34 KB still fits; harmless in the runs [disasm, PP's].
