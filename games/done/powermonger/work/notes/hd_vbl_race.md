# HD build: the late VBL after a GEMDOS call loses a mouse-button report (found on WW1, 2026-11-24; master AFFECTED [INFERENCE], NOT FIXED here; the WW1 fix is PARKED, not shipped)

Found on the WW1 port (`games/in_progress/powermonger-ww1/`, `work/notes/RESULTS_stage04d.md` section 7: evidence, traces, gates). Master's `patches/hd_core.s` has the same code (`tos_in` / `tos_out` / `replay` differ from WW1's only in the address of the game's byte processor, `jsr $18e8` vs `jsr $e7c`), so master's HD build has the same race [INFERENCE: not run on master; `tools/play.sh --hd --machine falcon` was started once, the harness's name gate does not match the Falcon screenshot (718 px wide), and the run was dropped for the WW1 work].

## Symptom
After a save or a load through the HD code, the FIRST mouse click is ignored (the one after it works). While the fault is latched the pointer also drags the overview map when it is moved over it (the game thinks the left button is still down). Seen on the Falcon (WW1, Hatari GEMDOS folder: 5 of 10 loads with the LOAD click held 0.10 to 0.34 s, i.e. released during the load); the same code runs on every machine, the odds depend on how long the GEMDOS calls take against how long the button is down. By hand the user did not notice it (WW1 Falcon HD: "rock solid").

## Mechanism
* The game runs the IKBD in absolute mouse mode and polls it: the VBL handler (master `$1286`, WW1 `$774`) first dispatches on the button byte of the LAST complete packet (master `$1c48f`, WW1 `$1d2af`: bit 2 = left pressed, bit 3 = left released SINCE THE PREVIOUS INTERROGATION, reported once) and then sends the next interrogation `$0D`. The ACIA handler copies each completed packet's button byte over that byte. Nothing consumes it: the design needs exactly one packet between two handler runs. The reply takes about 10 ms (Hatari: 18 000 cycles + 6 bytes at 7812.5 baud).
* The press handler (master `$1330`, WW1 `$81e`) ignores a press while the "left held" flag (master `$2df9c`, WW1 `$2edbc`) is set; only a release report clears it.
* `hd_load` / `hd_sector` run with SR `$2700` / `$2500` for the whole GEMDOS call (0.1 to 0.5 s). The VBLs of that time collapse into one pending interrupt, which the game's handler takes the moment the caller's SR is restored, i.e. at any point of the frame: a LATE handler run that sends `$0D`.
* If the next real VBL comes before that reply is complete (less than ~10 ms later, or the game starts the next HD call in between and both replies go through the FIFO), its handler dispatches the OLD byte and interrogates again. Two replies are now on their way back to back; the second (no change) overwrites the first before any handler run has seen it. If the first one carried the release of the click that started the save / load, the held flag stays set: the next press is ignored; its own release clears the flag.

## Fix tried on WW1 (`games/in_progress/powermonger-ww1/work/notes/hd_vbl_race_fix.diff`, `replay` of hd_core.s): PARKED
After the replay of the queued keyboard bytes, still at SR `$2700`: point `$70` at an `rte`, load SR with the caller's own saved SR (`move.w 16(a7),sr`: hd_load / hd_sector push it first) for two `nop`s (the pending VBL is taken by the stub), back to `$2700`, restore `$70` (9 instructions, 28 bytes). The game's handler then only runs at real VBLs: one interrogation per frame, as in the floppy build.
* Falcon (WW1): 0 of 5 loads lose the click; the full HD cell with 0.10 s clicks passes twice.
* **STE 1 MB (WW1): 2 crashes in 45 forced-win Retires with the fix** (`Address Error writing at address $55f09, PC=$13e0`: the VBL handler's button dispatch jumped through its 16-entry table with a button byte above 15 [INFERENCE from the stack: no return address between the handler's saved registers and the fault], i.e. a corrupt IKBD packet after the Retire's HD call). HEAD: 0 in 1 (+ 4 older cells); the equal-sized HEAD run was not made, so whether the fix causes it is OPEN. That is why it is parked.
* A second, separate hazard seen while reading the code, in master and WW1 alike [INFERENCE, not reproduced]: `tos_in` clears the MFP pending bit (`move.b #$bf,$d(a0)`) about 330 cycles after its `drain`. A keyboard byte that completes in between leaves the ACIA interrupt line asserted with no edge to come: `hd_acia` never runs, the rest of the IKBD reply (9 bytes per VBL, about 12 ms of every frame) is lost by overrun, the packet parser is left mid-packet (phantom key codes; if the train was cut right after its `$f7` header, the next `$f7` becomes the button byte and the VBL handler's table jump goes wild). The `drain` right after the clear, or not clearing the bit at all (`hd_acia` tolerates a stale pending bit: its `drain` finds nothing), would close it.
