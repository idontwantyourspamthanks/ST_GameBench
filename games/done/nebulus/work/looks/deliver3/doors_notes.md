# Nebulus: how a tunnel door finds its exit, and the editor's paired doors (NebDoors)

Tags: **[obs]** observed in Hatari (raw lines in `logs/`, scripts `work/editor/e203_study*.py`, `e203.py`), **[disasm]** read from `work/train/dis_33000_40000.txt`, **[INFERENCE]** not proven.
Built and gated in a COPY (`/tmp/nld`, RAM disk) on top of the deliver2 files (`work/looks/deliver2/`); the real tree is untouched except this directory.  `PATCH.diff` is against the deliver2-merged tree.  Scripts carry `/tmp/nld/...` scratch paths.

## 0. The user's report, answered
The frog does **not** look for the partner door.  Pressing Up inside a door cell walks him through the tower and out again **exactly half the ring away: x + 64 of 128 = column + 8 (mod 16), on the same y (row)**, whatever is there.  A door at the destination is only decoration for where he lands: with no door he simply stands (or falls) there.  So a door placed alone looks "wrong" in the user's words ("the frog emerges where the door should be, not where it is").  The editor now places the opposite door itself (section 4).

## 1. The mechanism [disasm + obs]
Frog variables: x `$33a16` (0..127, 8 per column, 4 = column centre), y `$33a18` (4 per row), facing `$33a1c` (`$80` right, 0 left), state `$33a20` (handler table `$39cd2`: 0 standing/ready, 1 walking, 2 jump, 3 turn, **4 tunnel**, 5 shoot [INFERENCE], 6 lift ride, 7 hit [obs: the flyer's hit, y rises], 8 fall, 10 death [obs sequence 7 -> 8 -> 10, and 8 -> 10 into the sea]), phase `$33a1e`.

1. **Entry** (walking state `$39d0e`, branch `$39db0..$39e08`): with no horizontal input and joystick Up (`$338f4 == 1`): `sub_03ab10` first (lift slab under the frog, section lifts.md), then `sub_03aae8`: the cell **in the frog's own row** `grid[x>>3][y>>2]` (a standing frog at y = 8 is in row 2, the ledge he stands on is row 1) must have bit 7 set and `(v & 3) == 3` (`$83`, `$87`, `$c3`), carry set; `d0 = v & $40`.  `$c3` (bit 6) = **exit door**: `$33a46 = 1` (level complete), then the same state; otherwise a tunnel door.  `$39e08 -> $3a116`: state 4, phase 0.
2. **Tunnel state `$3a12c`**: phase 0..3 centres x on the column (`x & 7` towards 4, one step per loop) while the walk-in frames play; at phase 4..6 `$3a1b4` stores the target **`$3a2f6 = (x + $40) & $7f`**; phase `$d..$1c` (`$3a1fc`): `x = (x +- 2) & $7f` per loop (`+2` when `$33a1c != 0`) until `x == $3a2f6` (32 loops, the frog is drawn as the tower turns round him; y is not touched).  For the exit door `$33a46 == 1` skips the walk and plays the finish.  **Nothing in this code reads the grid at the destination.**
3. **Emerge** (phase `$1d..$28`, `$3a258..$3a2e4`): walk-out frames; from `$3a282` on each loop calls `sub_039c2e(-4)` = y -= 4 with the collision test `sub_03a7ce` (a cell blocks when bit 7 is set and `(v&3) != 3`: pillars, ledges, blue blocks block; **doors and empty cells do not**); carry clear = free = keep falling, carry set = floor reached: the facing is taken from the joystick, state 0.  `y < 0` -> `$3a744` death (life lost).
So the answers: **always column + 8 (mod 16) on the same y; no door cell is required; an empty destination = the frog falls to the first floor below that row (the sea = death); a pillar destination = the frog is placed inside it, nothing checks (see below); the row never changes.**
4. **Two-way**: the same code runs from either door, so a pair is a two-way tunnel.

## 3. The original towers (all 16 imported with `ovl.py`/`nebedit`)
* Door cells: **534 x `$83`, 48 x `$c3`** (3 exit cells per tower), **no `$87` anywhere**; `$87` (bit 2 set) behaves as `$83` in the tests above [obs PAIR87 as a destination; Up inside a `$87` was not pressed: [INFERENCE] the same `(v&3)==3` test].
* All door runs are 3 cells tall.  **176 of 178 runs have a door on exactly the same rows 8 columns away** (88 pairs; e.g. M1 T1 (1,20)/(9,20), (1,43)/(9,43), (2,2)/(10,2), (0,39)/(8,39), (6,5)/(14,5)); the pairs always use the same code `$83` on both sides.  The two exceptions are M1 T8 column 2 and M2 T8 column 13, rows 92-94, whose opposite cells are the tower's exit door (`$c3`): the tunnel there lands the frog in the exit door.
* The door at the bottom of tower 1, (2,2) with its partner (10,2), is an ordinary tunnel pair beside the start, **not a start door**: the frog is placed at x 4, y 8 by the new-game init (`sub_039bb0`) and arrives by submarine (user confirmed), not through a door.  A frog start is never tied to a door.
* `$87` vs `$83`: both are door class for the game (`(v&3)==3`, collision-free, terrain class 40, drawn the same dark opening); the bit 2 difference is not used by the door code.  The editor places `$83` (as every shipped tower does).

## 4. The editor [implemented, section 16 of `work/notes/editor.md`]
* **Door opening** (menu item or `D`): places the 3 cells as before AND the same 3 rows in column `col ^ 8` (= (col + 8) mod 16: 3 <-> 11, 14 <-> 6, 12 <-> 4), code `$83` on both sides (the original codes).  Status line: **"Door + opposite"** (menu route and key route).
* **Delete / overwrite**: clearing (Empty, Del, C) or overwriting (any other tile, enemies, lift stop, the Exit door) one door cell also clears its partner cell **if that is a door**; a door cell whose opposite is not a door (old files, a lone door) is deleted alone and nothing at the opposite cell is touched.  (Simple per-cell rule: `cell(c,r) == $83  <=>  cell(c^8,r) == $83`; chosen over "delete the whole 3-cell door" because it is the same code path for every write.)  Placing a door over a non-door partner cell replaces it (a ledge or lift cell there is lost; e203 checks it).
* **Exit door** (`$c3`, the finish): 3 cells, not paired, status line **"Exit (finish)"**.
* Not paired (direct writes): Copy tower (originals are paired anyway), Blank grid, the lift code.  Old files with unpaired doors load, play and edit as before; **no load/play warning** (it would cost more than the 20 B allowed); dadprg lints them instead (section 6).
* Format: version 1, unchanged; no new cell codes.
* Budget (`gen_ed.py`): CODE1 5312 B (free 0, was 14), DATA 1324 (0, was 30), CODE2 1776 (16), CODE3 570 (6), CODE4 252 (4), CODE5 136 (2), CODE6 34 (4): total **9404 B, 32 B free** (deliver2: 9360 / 76 free).  New: `place` +38 B (reads the old cell, pairs), `a_tri` message +16 B, two strings 30 B.  Paid for by refactoring: `cur_cell` and the two column-base copies in `place_enemy` now call `colbase` (-42 B).  Nothing cut from the user-visible text.  `cur_cell` now trashes d2, so `a_ekey` keeps its kind in d4.  `nepatch verify`: 33 verified sites, 3 clear ranges, 11 blocks; `nefloppy selftest`: all `yes`; floppy build 419840 B.

## 5. The frog inside a wall [obs]
With enemies off (E trainer; `logs/study2_stuck_enemies_off_ste.log`): arrived at x 68, y 8, state 0 inside the pillars at (8, 2-4); 3 s without input: unchanged (no damage, no push-out); Right 0.8 s and Left 0.8 s: x stays 68, state 1 (walking: every step is blocked by the pillars); Up: nothing.  So the frog is **stuck inside the wall** (he can try to walk, not move; no life is lost by it; whether a jump gets him out was not tried).  (The first run, `study2_ret_stuck_ste.log`, showed states 7/8 with the flyer on: that was the pink time-waster killing him, not the wall.)  A pair placed by the editor never lands the frog in a wall (the destination column is a door cell), which is another reason for pairing; a hand-made file can still put a pillar there.
