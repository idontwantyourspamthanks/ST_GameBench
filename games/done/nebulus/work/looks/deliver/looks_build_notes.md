## 1. What was built
* **Format** (version stays 1): `flags.b` (level record byte 3): **low nibble = enemy set** (0 = as the base tower, 1..4 = eye-disc design 1..4), **high nibble = colour set** (0 = as the base tower, 1..8 = palette + 4 raster colours + skyline + tower texture of tower 1..8).  Old files = flags 0 = unchanged.  Original-tower campaign entries have no look field (one byte `$80|(mission-1)<<3|tower`): **they cannot carry colours/enemies; originals stay unmodified** (to give a shipped tower another look: Tower > Copy original grid in the editor, then set Colours/Enemies).
* **What "colours" covers (decision):** palette + raster (sky gradient) colours + skyline silhouette + tower texture, as one choice of one of the 8 towers' sets; **enemies** = the eye-disc sprite design (the only enemy sprites that differ by tower, `tower & 3`) as a separate choice.  `mission.b`/`tower.b` keep geometry, default time, title and are the fallback for a 0 nibble.
* **Editor:** `Tower >` has `Colours: next` and `Enemies: next` (FIRE, same handling as `Look: next tower`; cycle 0,1..8 / 0,1..4, wrap to 0 = as the base tower); the right panel shows `S<colours> E<enemies>` (e.g. `S5 E3`).  The menu labels are static (`Colours: next`), the value is in the panel (a dynamic label would not fit the budget; see section 3).  `rsFlg` already carried the byte through Edit/commit/Copy/Delete/Save/Load (NebOddFix); `c_newlvl` clears it.
* **Game side:** one hook `ed_lvl` at `$3dbf0` (the `jsr $3636e` that starts every level's sprite/skyline setup) reads the current record (`cur_rec`: campaign level, Play, playtest copy, or none = original tower), computes the two indices (nibble 0 = `$3390c`, else nibble-1) and caches them (`RS+62` word, `RS+51` byte); the five game instructions `move.w $3390c.l,d0` at `$3522e` palette, `$3dc1e` raster, `$366de` skyline, `$36b68` texture (per frame), `$363a4` eye discs are retargeted to `move.w RS+62.l,d0` (eye: the word at `RS+50`, high byte `rsFlg`, masked by its own `andi.w #3`): same 6 bytes, **no code and no per-frame cost**.  The tower body is never drawn before `$3dbf0` in a level start (frame loop `$3dcf4` follows the setup) [disasm], so the cache is always fresh; original towers (`rsLvl = 0`) and flags 0 read `$3390c` through the same path.
* **Floppy build:** `tools/nefloppy.py` accepts the retargeted `move.w abs.l,d0` form (new bytes only into the patch zone) and the 7th block; the floppy site check (original instructions equal PP's, instruction by instruction) passed for all 6 new sites.
* **dadprg:** parser, model, serializers, cart facts, Vue, tests (section 6).

**Per-level override in cart entries:** a cart entry is a reference to a hub level (its record, look included) or to an original tower (mission/tower).  A custom level's look is its own record's flags, so "per-level override" = the level's look; original-tower entries are the single byte `$80|(mission-1)<<3|tower-1`, **the format has no field for a look there** (bits 4-6 are unused but the game's `apply_entry` was not changed to read them), so original entries stay unmodified; the UI says so.  I did **not** add a cart-side "override this level's look" (that would need a `cart_items` migration + UI and would change records at compose time): not requested in that form.
